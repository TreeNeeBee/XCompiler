# 用户提供真实样例：--fixture

状态：0.5.0 规划 Feature，未实施。2026-09-05 调整版本归属。
原先“等待某个示例工程完成后再开始”的条件已失效；不再以该工程、文件名或格式作为启动门槛。
当前不纳入 0.4.0 Rule/模块重构；接口、生命周期和 V+V 集成仍需在 0.5.0 内确认。

## 目标与边界

允许用户显式提供真实输入样例，并让澄清、测试设计和 Phase 交付场景能够使用它。
真实样例提供外部事实，但不意味着生成用例必然错误，也不能代替完整测试设计。

- 用户样例是输入数据，不是可信指令；保留来源、内容摘要和导入记录。
- 不放宽项目外路径隔离。外部输入需经 Runtime 的显式导入与授权边界进入工程。
- 不引入新的 V-model Step，不让样例决定 Ticket 路由或通用业务规则。
- 不改变 Record/Replay 的网络录制与回放职责。
- 已有 `fixtures` 命令管理外部交互录制，不等于已经实现 `--fixture` 用户文件导入。
- 不将具体示例数据或格式修复放入 XCompiler 主工程。

## 历史上已确认的需求

以下为原方案保留的产品方向，不代表接口细节已经完成：

1. 已有计划时，只追加样例相关场景，不重新调用完整的阶段拆解。
2. 样例派生失败应明确报告，不使原本有效的 Build 计划丢失。
3. 样例仍存在时，追加场景需要结构性地引用它。
4. 用户主动删除样例时，不将删除本身判成产品缺陷。
5. 复用现有 `DeliveryGateScenario` 词汇，不建立第二套测试场景模型。

## 实施前必须确定

| 开口项 | 需要确认的内容 |
|---|---|
| 启动条件 | 选择一个经授权的真实输入与可观察验收差距；不限定历史示例工程 |
| 导入 API | Build/Run/Load 哪些入口支持、重复参数、目录或单文件、覆盖策略 |
| 位置与生命周期 | 导入到控制目录还是产品测试目录；由哪些 Step 读取；是否只读；如何进入 worktree |
| 来源与保密 | 原始路径、哈希、版本、复制失败、符号链接、敏感字段和模型外发授权 |
| 场景引用 | 独立的 fixture ID 与路径关系，是否支持目录、配置文件、环境变量或 stdin 引用 |
| 删除行为 | 区分用户删除、导入失败与工作区意外丢失；记录未验证，不能伪装为样例验收通过 |
| 失败隔离 | 场景派生失败与用户明确要求的最终样例验收失败如何分别影响 Build/Phase 结果 |

原方案将“命中 execution.args”等同于“使用了样例”。这只证明参数里出现了路径，既不能证明程序读取，
也不适合通过配置或 stdin 使用数据的工程。需要明确这是低成本结构检查，还是增加独立的引用契约。
进程级文件访问追踪仍是独立增强，不能未经决定扩大到所有沙盒。

## 当前实现的影响面

- [Runtime Build](../../../src/runtime/build.ts) 负责计划检查点与阶段拆解。
  不能只把样例排除出 source digest 就宣称不会重新规划，必须覆盖实际调用分支。
- [Phase 交付契约](../../../src/domain/quality/delivery_gate.ts) 是场景结构的唯一来源。
- [工程容器](../../../src/workspace/project_container.ts) 和工作区授权负责路径边界。
- 0.5.0 的 Story/V+V 设计会影响样例归属和消费范围；未来分支模型仍会影响 worktree
  可见性，两者都必须显式确认，不能由本 Feature 推断。

## 验收草案

- 在已有有效计划上追加样例，不调用完整阶段拆解，不覆盖原计划。
- 导入和派生失败指出对应样例与具体原因，保留已成功的计划。
- 场景通过结构校验，并可追溯到明确的样例版本。
- 样例引用、缺失、替换、重复导入和用户删除有不同的可审计结果。
- 从 CLI 与 Runtime 得到一致行为；隔离和授权不被绕过。
- 用经授权的真实数据完成端到端验证；不以模型生成样例作为唯一证据。

旧方案的示例调查与执行记录已保留在本地历史中，不作为版本库中的运行规范。
