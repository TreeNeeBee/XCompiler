# 0.5.0: functional Stories and V+V development

Status: initial iteration direction confirmed; detailed architecture and implementation not approved.
Recorded 2026-09-04 against the current-code baseline `77ff6e2`.

## Release boundary

The user has assigned the Story/Task redesign to 0.5.0. The confirmed direction is:

- Restore Story to a functional item, rather than a wrapper for one V-model Step.
- Place a V-model development flow within each Story.
- Integrate a V-model flow within Epic as well, forming the proposed **V+V** structure.
- Design Story/Task relationships and execution around a structured development process.

V+V is the working name for this project direction, not a claim that a detailed standard or an
executable state machine has already been selected. This document is an iteration proposal, not a
request to implement 0.5.0 now.

[0.4.0](../0.4.0/0.4.0-modularisation-and-layering.md) focuses on Rule architecture and module separation.
It does not remove `workKind`, replace stage Stories with functional Stories, independently schedule
Tasks, introduce nested V-models, or replace CR propagation with a new Story carrier.

## Current implementation versus target direction

| Concern | Current implementation | 0.5.0 direction or open design |
|---|---|---|
| Project evolution | Multiple implementation Phases; detailed planning of the current Phase | Retain iterative development; define how Epic/Story planning fits it |
| Phase and Epic | One Epic per Phase | Starting point for discussion; specify their separate responsibilities |
| Story | Eight stage Stories and one delivery Story per materialized Phase | A functional item with its own V-model flow |
| Epic | Phase-level work aggregation and delivery record | An outer V-model flow coordinating its functional Stories |
| Task creation | Step `subTasks` compiled into up to two levels of Task records | Decomposition timing, granularity, and owning role remain open |
| Task-to-Step relation | `stepId` fixed at compilation from the parent Step | Define which V instance and Step own each Task |
| Assignment | PM assigns a Ticket to an Actor; child Tasks inherit their parent Story's assignment | Distinguish Step allocation from Actor assignment explicitly |
| Task execution | Parent stage Story executes; children start and complete as a group | Define individual execution, evidence, and completion contracts |
| V-model state | Eight Phase Steps, their dependencies and pairings, coordinated by PM | Define Epic-level and Story-level flow identity and state ownership |

## Conceptual structure

The following is a responsibility sketch, not a persistence schema or an execution order:

```text
Project: iterative development
  Phase: iteration objective and delivery boundary
    Epic: outer V-model
      Functional Story A: inner V-model
        Tasks: related to an owning V-model Step and assigned to Actors
      Functional Story B: inner V-model
        Tasks: related to an owning V-model Step and assigned to Actors
```

Proposed responsibility split for review:

- The Epic V establishes the iteration/system context, shared contracts, and integrated acceptance.
- Each Story V develops and verifies a functional item within the accepted Epic context.
- Tasks describe concrete work. A Task's owning Step and its assigned processor are separate facts.
- PM coordinates dependencies, progress, and routing across these scopes. The technical owner
  supplies the context and evidence for work and findings.

These responsibilities still need an explicit agreement on outer/inner stage coupling. The diagram
does not mean running the Epic V to completion before starting Stories, running every Story
sequentially, or automatically passing the outer V when all inner Vs pass.

## Design decisions required before implementation

| Decision | Questions to settle |
|---|---|
| Phase/Epic ownership | Does Phase retain its own executable Steps, or coordinate an Epic-owned V? Which object owns the delivery verdict? Avoid two authoritative copies of one flow. |
| Story decomposition | Are functional Stories identified during Phase planning, Epic requirements, or Epic architecture? When are their scope and acceptance baselined, and when may they be refined? |
| Task decomposition | Are Tasks planned up front or decomposed by the owner as each inner stage becomes ready? What granularity and hierarchy depth are appropriate? |
| Step allocation and assignment | When is a Task bound to a particular V instance and Step? When does PM choose an Actor? How do reassignment and delegation preserve ownership and evidence? |
| Outer/inner stage coupling | Which Epic artifacts permit Story work to start? Which Story results are prerequisites for Epic integration and acceptance? Define dependencies without cycles. |
| V definitions | Do both levels use the same eight Step types and pairing rules, or different contracts? How is first-pass baseline deferral determined when some product code already exists? |
| Delivery and evidence | What are Task, Story, Epic, and Phase completion conditions? Which checks are independent, and which exact-revision evidence may be reused without duplicating test execution? |
| Corrective routing | How are local defects, shared-interface changes, missing coverage, and external findings routed between Story and Epic scopes? Which changes invalidate sibling Story evidence? |
| Identity and recovery | How are V instances, Steps, executions, and findings identified? How do interruption, reopening, cancellation, and repeated findings avoid duplicate work and false closure? |
| `workKind` and Ticket structure | Remove the universal field, replace it with typed relationships, or retain narrower distinctions? Do not decide this merely by renaming the field. |
| Cross-stage change carrier | Does the earlier carrier-Story proposal still fit functional Stories? Compare an accepted change record or another explicit relation before reserving a second meaning for Story. |
| Workspace and integration | How do independently developed Stories share or isolate work? Branching and ChangeSet/MergeRequest consolidation require separate approval; they are not implied by V+V. |

Multiple inner Vs will contain similar stage names. A displayed S004, role, or stage type alone cannot
identify the correct repair target. The approved schema must preserve global identity and the
owning flow context through assignment, failure evidence, gates, and recovery.

## Guardrails for the future design

- Preserve Runtime as the only business entry, PM coordination, Domain transition authority, and
  canonical persistence. New flow views must not become competing lifecycle stores.
- Do not automatically close unfinished children when a parent passes. Do not infer integrated
  acceptance solely from the number of completed Stories or Tasks.
- Preserve original error evidence, independent finding identity, scoped incremental changes,
  exact failure verification, and Debug Wiki provenance across the two V levels.
- Preserve test-defect, product-defect, missing-coverage, contract-change, dependency/environment,
  and permission distinctions. Nesting must not turn every outcome into a generic Bug.
- Reuse 0.4 Rule definitions where applicable, while binding execution to the correct owner, scope,
  context, and rule revision. Reuse of a definition does not imply reuse of its passing verdict.
- Record/Replay and live acceptance need declared owners, data provenance, and permission boundaries
  at the appropriate level. Nested flows must not silently duplicate paid/network operations.

## Planning deliverables

Before starting implementation, prepare and review:

1. Object and ownership model for Project, Phase, Epic, functional Story, V instance, Step, and Task.
2. Outer/inner flow diagrams with entry conditions, gates, failure routes, and terminal outcomes.
3. Story and Task decomposition contracts, including the exact planning and assignment moments.
4. An end-to-end walkthrough with at least two Stories and a shared contract change, including
   individual delivery, integrated failure, affected-scope reopening, and recovery after interruption.
5. A change-impact map for the compiler, PM scheduler, execution unit, Rule context, persistence,
   workspace integration, reports, and tests.
6. Acceptance cases proving that another Story's passing gate cannot close this Story's defect,
   and that parent delivery cannot conceal incomplete child work.

These are design-review outputs, not approved field names, state transitions, or implementation
milestones. Resolve the open contracts with the user before coding.
