Status: deferred discussion, removed from the active 0.4 scope on 2026-09-04.
The filename is retained for existing references; it does not assign this work to release 0.4.
Execution and lifecycle details remain unresolved in decisions D02, D03, D06, and D07.
Reviewed against `77ff6e2`.
See the [decision register](0.4.0-decisions.md) and [refactor outline](0.4.0-modularisation-and-layering.md).

0.4 now focuses on Rules and module separation. Story/Task redesign is initial
[0.5 V+V planning](../0.5.0/0.5.0-functional-stories-and-v-plus-v.md), where Story represents a functional
item. The carrier Story proposed below needs reconsideration against that meaning. The following is
the earlier proposal, not current behavior or implementation approval. Branch redesign and merge
object consolidation are not automatically part of 0.5 either.

"Stage" means one V-model Step (S001-S008), not an implementation Phase.

## Previously discussed direction

| Branch | Lifetime | Purpose |
|---|---|---|
| `master` | Permanent | The only authoritative product tree and release source |
| `dev` | Permanent | In-progress stage work, which may be incomplete between gates |
| `xcompiler/ticket/<ticketId>` | One corrective work item | Bug or CR development; exact generation/re-entry policy remains to be defined |

Stage work commits to dev. Bug/CR branches merge into dev without a separate product-quality gate or
merge request. A stage promotes dev to master through a stage-level merge request only after its
delivery conditions pass. Rejected promotion leaves the work on dev.

Development debugging on dev does not create a new Ticket for each failed attempt. Attempts, errors,
changes, and evidence must still be recorded, and the stage's own work remains subject to
non-convergence limits. "No Ticket" does not mean no record or unlimited retries.

## Routing is not downstream propagation

A Bug still goes through PM to the Step that owns the repair, including an earlier V-model Step.
After repair, Bug/CR work stays stage-local instead of creating a chain of downstream CR children.

Cross-stage change responsibility moves to a PM-owned Story. On V-model advancement, PM examines
open carrier Stories and materialises local CR work for the entering stage. A stage receives the
accepted delta and original context, rather than relying on the previous stage's completion prose.

This carrier choice is now deferred, not a prerequisite for 0.4. Its surviving evidence and impact
requirements must be reconciled with functional Stories before a replacement is approved.

The existing per-Step `v-model-step` Story and the new carrier Story are different roles.
D03 must define their type distinction, consumption policy, and completion rule before implementation.

## Gate contract still needs approval

The original sentence "baseline passes, therefore merge" is not a complete replacement for the current
Step delivery contract:

| Current stage | Gate classes |
|---|---|
| S1-S4 | Deliverable validation plus paired baseline tests |
| Initial S1-S3 | Deliverable validation still required; baseline execution explicitly deferred until code exists |
| S5-S8 | Baseline plus approved supplemental functional tests, frozen before execution, with KPI/tolerance checks |
| Phase delivery | Integrated deliverables and declared real-user scenarios, using real external services when required |

D02 recommends retaining these classes and avoiding duplicate execution at the dev merge boundary.
This table records current behavior to preserve or explicitly supersede; it is not a new approval.

Permission, path, conflict, revision, and data-loss checks are separate from product-quality gates.
The phrase "no gate into dev" must not silently remove them.

## Ticket creation is not fully specified

The original proposal names two sources:
- A verification-stage gate finding a defect creates a Bug.
- A master promotion requiring downstream work creates a carrier Story for PM.

That list is incomplete relative to current contracts. D02 must also cover Phase delivery intake,
test incompleteness/quality Enhancement, dependency requests, test-versus-product defects, and
permission/environment failures. Do not infer from their omission that all become Bugs or disappear.

Discovery context and PM ownership must remain explicit. A stage owner supplies technical evidence;
PM routes registered work. Phase-external observations use PM intake rather than fabricating a
Phase-local discovering actor.

## What the current code actually does

| Area | Current implementation | Target direction or gap |
|---|---|---|
| Long-lived work branch | Master is canonical; no permanent dev contract | Add dev with explicit lifecycle/recovery semantics |
| Initial candidate creation | CODE Story creates a ChangeSet; non-CODE work can initially bind canonical | Move ordinary stage work to dev |
| Other candidate creation | Rejected canonical work can be preserved as a candidate for any Ticket | Replace this rollback mechanism only after dev retains the failed revision equivalently |
| Existing bindings | A correction can inherit its lineage worktree across Step types | Define one Bug/CR branch, discovery revision, and re-entry behavior |
| Promotion granularity | Ticket integration is orchestrated per attempt/work item | Stage-level promotion, with repeated rejected attempts represented explicitly |

## Obligations that survive removal of the CR chain

- Original failure identity, scene, discovery worktree, and accepted requirement.
- Scoped incremental changes rather than full regeneration.
- Each affected owner's impact verdict, change record, and verification evidence.
- Bug `resolved` versus `closed`, original-failure replay, recurrence, and Debug Wiki eligibility.
- Failure/error history, model scoring provenance, and independent finding identity.
- Recovery and idempotency when interruption occurs between persistence and handoff.

Delete obsolete functions and fields only after their surviving obligations have a new owner.
Not every repair made around the old mechanism is itself obsolete.

## Open lifecycle work

D03 covers Story receipts and closure; D06 covers ChangeSet/MergeRequest; D07 covers shared dev.
In particular, a permanent branch does not by itself solve:
- Rollback when downstream changes are already on dev.
- Concurrent writers or a changed candidate after the gate evaluated it.
- A failed ticket-branch merge or interrupted master promotion.
- Manual edits to generated projects.
- Reopening previously consumed stages after a revised Story.

No implementation should select these behaviors silently.
