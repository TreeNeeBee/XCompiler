## Rescan classification

The inventory has 14 instruction groups (P), eight judgement/review groups (J), and 20 framework
groups (F). These are review groupings, not counts of approved RuleLists or assigned slots.

- **P: instruction extraction.** Move reusable instruction text into versioned Rules; preserve its
  meaning and typed inputs. A prompt describing a gate does not replace the gate implementation.
- **J: semantic judgement.** A Rule can define the rubric, evidence, and typed output. Replacing a
  heuristic or reusing a verdict changes behavior and requires approval, not just file migration.
- **F: framework definition.** Keep state, authority, security, effects, and mechanical facts in code.
  Their explanation may appear in a Rule, but their enforcement cannot become optional prompt text.

Mixed files must be split by responsibility. None of these labels authorizes copying an entire
module into Rule text or promoting repository-maintainer constraints into generated-project policy.

The 2026-09-07 Rule categories are a separate axis: general development/language, compiler framework,
functional scenario, and generated-project business Rules. P/J/F remain source-review groupings,
not those categories. In particular J06 is a scenario rubric; J08's existing Wiki retrieval remains
a debugging-experience branch and is not an implementation of RuleSelector. RuleLists occupy one
slot each and support lookup of individual Rules; extraction need not load every Rule in a list.
See the [RuleChain contract](0.4.0-rulechain-design.md) for the clarified assembly and Wiki boundaries.

## Invocation and extraction traps

- Four business `.chat(...)` sites exist: Planner clarification and its shared plan-retry caller,
  StepExecutor, and the scenario judge. Three Router call sites plus `PluginHost.wrapLLM` are
  wrappers, not independent business planners. All business entry paths and retry/Plugin paths
  need coverage for mandatory base loading.
- `Role` personas and `DomainRole` ownership are different sets. Tester covers integrator and tester;
  Debugger is a corrective execution persona, not an extra Domain owner. A slot cannot replace
  `roleForStepType` or grant a Tool.
- `core/quality_gate.ts:evaluateQualityGate` still has no production caller found by the rescan.
  Its default/shape helpers are used. Do not delete the whole module or wire the unused evaluator
  into production merely to demonstrate Rule enforcement.
- Current `stepContextFingerprint` hashes inputs/outputs/`systemPrompt`, not external Rule content.
  Externalizing the instructions requires effective-version identity in recovery and audit.
- Current compaction preserves the first system message, while Plugin `llm.before` may replace the
  messages. Mandatory rules need an approved final assembly/integrity boundary, not an early prefix
  that can disappear later.
- `agents/calibration.ts` still performs plan calibration; only diagnostic-advice helpers moved to
  Wiki. Planner and Router already generate repair feedback, and `parseTurn` repairs candidates
  that the stricter completion predicate rejects. Consolidation must distinguish protocol repair,
  plan transformations and knowledge reuse, and remove overlapping retry ownership at the callers.

See [impact review](impact-review.md) for the implications and required design decisions. This rescan
does not approve deletion of heuristics, revised gate behavior, or model-based identity matching.

Important asymmetries:
- Step permits `closed -> reopened`; Phase does not.
- Project permits `closed -> planning`; that alone does not implement Phase reactivation.
- Ticket permits `cancelled -> reopened/closed`, while its `closed` state is terminal.
- Plan-phase status is not the domain Phase lifecycle; do not merge them into one store by spelling.
- ChangeSet and MergeRequest already carry merge state. What is missing is simpler orchestration
  linking those states to Step/Ticket/Phase, not a nonexistent merge state machine.

Transition legality is guarded by `util/state_machine.ts`. Application still coordinates scheduling,
execution, evidence, persistence, and side effects.

## Typed decisions and their limits

| Decision | Current contract/owner | Caution |
|---|---|---|
| Scenario outcome | PM judge: ok, reason, evidence; failed verdict requires ticketType and target | Invalid JSON or classification is rejected, not defaulted to Bug |
| Execution turn | thoughts, actions, done, qualityAssessment, CR/validation disposition | Completion predicate collapses several rejection causes |
| CR disposition | applied/not-applicable plus typed reason and inspection evidence | Current chain remains in 0.4; preserve impact reasoning when extracting rules |
| Stage quality | assessment, metrics, tolerance, findings | Follow the actual runner and PM call sites, not just an exported helper |
| Gate finding | seven categories and six targets | Different stable codes must remain independently actionable |
| Plan/clarification | validated model output interpreted by planning workflow | Content decisions and schema errors are different outcomes |

Current finding categories are test-defect, product-defect, change-request, test-incomplete,
quality-shortfall, deliverable-defect, dependency. The earlier count of six categories was incorrect.

An ordered evaluation rubric is a useful pattern, not a universal parser fallback. A protocol status
or the presence/absence of credentials never alone establishes that an implementation is wrong or
that an accepted capability must change.

## Selecting the first RuleLists

The [RuleChain contract](0.4.0-rulechain-design.md) now fixes language/role slots, exclusive range
indexes, protected base loading, and cross-list priority. The instruction extraction list and
selection/evaluation mechanics remain open; see D04 in the [decision register](0.4.0-decisions.md).
Recommended review sequence:
1. Name the production decision point, owner, inputs, output type, and evidence.
2. Classify each instruction as retained invariant, obsolete mechanism, optional advice, or disputed.
3. Assign level, evaluator, applicability, and version semantics explicitly.
4. Prove both selection and enforcement at the caller, including missing/contradictory rules.
5. Defer inline loop-control extraction until the owning flow is explicit.

Export count, line count, and one project's incident history are sizing aids, not evidence that all
rules are correct or equally reusable. No sample repair is automatically promoted into core policy.
