# 0.4.0 RuleChain 修订合同（草案）

日期：2026-10-18。状态：**已确认，实施中**（内容草案另行审定）。
依据：2026-10-17～18 对 RuleChain 现状的核对与讨论。现状、偏差和发现的问题见本文第 1 节；
已确认的选择见第 2 节；第 9 节列出仍需确认的事项。

本文确认后，第 2 节各项作为 D-22 起的决策写入 [变更清单](2026-10-15-review-change-list.md)，
被修改的原合同在对应文档中加替代说明。

## 1. 起因

核对发现（详见对话记录与 审计日志）：

1. **选择只用了一半。** 原设计分两层：适用性（数据匹配，硬过滤）和相关性（向量检索，低分交 LLM 评审，Q4 C）。
   业务流程可以把某些 Rule 指定为必需，其余适用的 Rule 作为可选，走相关性选择。
   0.4 把语言、角色、工作三段定为"只能绑定"：整表必需，不进相关性选择。可选候选池因此为空，检索和评审在生产中从不运行。
2. **粒度太粗。** 语言列表只能整表绑定。澄清和阶段规划也会收到 9 条 TypeScript 构建规则。
3. **同一约定两处来源。** TypeScript 约定同时写在 Executor 系统提示和 `0x0101` 里，规划第二遍提示又重复了一部分；
   Python 提示里已漏进 Vitest 专用写法。
4. **元数据不足。** Rule 没有名称、时间戳和内容摘要；检索摘要 `retrievalDescription` 多为位置标签，且只有英文。
5. **渲染问题。** 每条 Rule 带两个 UUID 和两个版本号，约占 Rule 块三分之一；列表内按 UUID 排序，使正文中"第一条"之类的引用错位。
6. **列表间引用不生效。** `references` 在加载时会校验、也写进快照，但绑定和选择都不会把被引用列表的 Rule 带入请求。
7. **没有 Python 语言列表**（`0x0102` 为空），也没有代码规范。

## 3. 选择模型

### 3.1 两层判断

| 层 | 回答的问题 | 判断方式 |
|---|---|---|
| 适用性 | 这条 Rule 能否用于本次请求 | 列表和 Rule 声明的范围（项目、语言、角色、工作）做数据匹配，与现状相同 |
| 相关性 | 可用的 Rule 中哪些与本次任务有关 | 只对可选候选做；方式见 3.3 |

### 3.2 最小规则集：必需条目由代码指定（R-1）

- 绑定计算保留现有的列表顺序：语言 → 代码规范（经引用）→ 角色 → 共享片段 → 模式片段 → 基线延后片段 → Step 工作 / 操作工作。
- **最小规则集**是下一版发布的 Rule 最小功能集：每类工作在这一版中必须携带哪些 Rule。它写在绑定计算代码中（`MINIMUM_RULE_SET`），按 `<列表 UUID>/<短键>` 引用 Rule（见 4.1）。
- 最小规则集按用途分组，组名说明它服务的场景：
  - `codeAndTests`（编码与测试）：Step 工作写代码、写测试、修 Bug、改 CR 时必须遵守的条目，包括配置归属（CODE 不重写基础配置）和开发依赖；
  - `projectSetup`（项目配置规划）：拆解时决定项目配置和各 Step 产出路径所需的条目。
- 列表中不在最小规则集里的条目不进入本次请求，也不产生选择调用（见本节末尾）。
- 角色列表、工作片段列表和 Step 工作列表仍整表必需：它们条目少，而且本来就按工作绑定。
- ~~`required_inapplicable` 错误只用于最小规则集中的条目。~~ 2026-10-19 起按 11.4：最小规则集中的条目也按适用维度过滤，不适用时跳过；`required_inapplicable` 只用于调用方直接交给选择准备的必需 Rule。

当前的最小规则集（已确认，见第 9 节）：

| 工作 | 语言列表中的最小规则集 | 可选选择 |
|---|---|---|
| `design.high-level` | 全部 | 否 |
| `analyze.requirements`、`design.detailed`、`code.implement`、`verify.*` | `codeAndTests`：测试框架、测试文件命名、本地导入、时间冻结、配置归属、开发依赖 | 否 |
| `repair.debug`、`change.apply` | 与被修复或修改的 Step 工作相同 | 否 |
| `plan.decompose` | `projectSetup`：项目配置归属、`package.json` 脚本、开发依赖、tsconfig 范围、测试文件命名（Python 对应条目） | 否 |
| `plan.clarify`、`plan.phase` | 无（不绑定语言列表） | 否 |
| `judge.scenario`（场景结果判定） | 无（现状不绑定语言） | 否 |

"优先级声明"在第 6 步移入基础段的级别定义（O-5），不再属于语言列表。

**0.4 不对语言列表做相关性选择（用户 2026-10-19 决定）：** 语言列表中带哪些条目完全由最小规则集决定，任何工作都不提供可选候选。
- 原因：可选候选只有 TypeScript 的 4 条项目配置条目，它们是否适用由工作类型就能确定。交给模型挑选，会让每个 TypeScript Step 多一次调用和一个失败点，而模型只凭一句任务摘要和一句描述判断，结果也不稳定。
- `package.json` 脚本、tsconfig 范围只属于编写这两个文件的高层设计（整表）和拆解（`projectSetup`）。
- 相应地取消"绑定提供可选候选"的路径。语言、角色、工作列表的条目只能作为必需进入请求，快照校验也恢复为"绑定段的 Rule 不能是可选"。
- 向量与摘要两种选择方式保留，只用于开放段（3.5），0.5 起配合分区与列表级选择使用。

实施中的修正与补充（2026-10-19，第 4+5 步）：
- **`plan.decompose` 加入测试文件命名。** 初版表漏了这一条。该 Rule 的正文针对的就是"Step 声明了 `tests/test_service.ts`"，而 Step 的产出路径由规划声明；已有的回归测试（来自一次实际运行）也要求规划能看到它。去掉它会让已修复的缺陷重新出现。
- ~~角色列表、工作列表和基础段永远整表必需，可选候选只能来自语言、Debug 和业务段。~~ 已由本节末尾的决定取代：绑定段（语言、角色、工作）和基础段的 Rule 都不能是可选。
- **`rule rm` 当前置空**（用户 2026-10-19 决定）：保留命令名，执行时输出 `rule_command_disabled: rm` 和"该功能当前无效、未做任何修改"的说明，退出码 1，避免脚本误以为删除成功。本地差异层不再记录删除，删除的语义以后再定。

### 3.3 可选候选的相关性选择（R-2）

- **配置了 embedding：** 按 Q4 C。向量检索后，分数达到阈值的直接采用，低分交 LLM 评审。
- **没有配置 embedding：** 把全部可选候选的摘要直接交 LLM 选择，不做向量检索。
- 两种模式都每次执行只选一次（D-6），结果固定在快照中。选择调用使用本次请求角色的模型池，额度和失败处理沿用现有评审机制（认领、额度、失败不重发）。
- **发给选择模型的候选不再使用 UUID：** 用临时短键（`c1`、`c2`……）配 `name` 和 `description`，模型返回短键，由代码映射回 Rule。评审协议版本随之升级。
- **查询文本只含任务摘要和错误摘要：** 不再把含项目 UUID 的上下文 JSON 编码进向量。
- 0.4 没有可选候选：语言列表全部由最小规则集决定（3.2 末尾），开放段仍为空。

实施中的补充（2026-10-19，第 5 步）：
- 两种模式走同一个入口：检索时不给向量检索器（未配置 embedding）就进入摘要模式。只要有可选候选，结果就带上本次的查询，由草稿记录；评审需要的查询只有这一个来源。
- 摘要模式的候选按 Rule UUID 排序，分数一律为 0。候选数超过 `rules.retrieval.max_candidates` 时报 `too_many_candidates`，不截断：没有分数时按 UUID 截断没有相关性意义。处理办法是调高上限或配置 embedding。0.4 默认上限 20，TypeScript 可选候选最多 4 条，不会触发。

### 3.4 列表间引用的绑定语义（R-5）

- 绑定一个列表时，它通过 `references` 引用的列表一并绑定，引用的传递关系由加载时的环检查保证有限。
- 被引用列表中适用的条目作为必需，不适用的直接排除。
- 被引用列表保留自己的槽位和适用范围：引用不提升优先级（原 Q3），渲染时显示在自己的组中。
- 快照中记录本次经由引用带入的列表和版本。

### 3.5 分区：按工作决定检索哪些开放段（用户 2026-10-19 决定）

基础段之外、不经绑定的段称为开放段：框架段、Debug 段、业务段。相关性选择只在本次工作的分区中找候选。分区表和最小规则集一样由代码指定（`RULE_PARTITIONS`，`src/domain/rules/partitions.ts`），确定、不增加调用：

| 工作 | 检索的开放段 |
|---|---|
| 各 Step 工作、`change.apply` | 框架、业务 |
| `repair.debug` | 框架、Debug、业务 |
| `plan.clarify`、`plan.phase`、`plan.decompose`、`manage.project` | 框架、业务 |
| `judge.scenario`（场景结果判定） | 无：只读自己的评分规则 |

- Debug 段的经验只服务于修 Bug；业务段服务于构建和规划产品的工作。
- 请求没有指明工作时，所有开放段都可检索：没有场景可以据以选择。生产中的业务请求都经过绑定，总带有工作。
- 分区只限制可选候选。绑定显式要求的 Rule 不受分区限制。
- 快照校验同样检查：可选候选必须来自本次工作的分区。
- 0.4 的开放段都还是空的，分区表目前没有可观察的效果。

**列表级选择（0.5 实施）：** 开放段有了内容后（Debug Wiki、业务规则），先按分区，再按列表表头选出相关的 RuleList，最后在选中的列表内选条目：
- 列表需要增加描述字段（表头只有标题，不足以判断相关性），这会改 schema 和摘要；
- 配置了 embedding 时对表头做向量检索；没有时由模型按表头选列表，这意味着两级选择、两次调用；
- 快照记录分区和列表一级的选择结果，评审协议相应升级；
- 它也取代摘要模式下的 `too_many_candidates` 报错。

## 4. 元数据（R-3）

### 4.1 精简后的结构（R-10，`schemaVersion: "2"`）

身份（用户确认）：

- **RuleList：** 使用完整 UUID（`id`），引用、清单、快照都用它。
- **Rule：** 保留完整 UUID（`id`）作为身份；**短键**取 UUID 的前 8 位十六进制（小写），由 UUID 推导、不另存字段。
  - 同一列表内短键必须唯一，由加载校验和 `rule add` 保证；冲突时 `rule add` 重新生成 UUID。
  - 跨列表定位写成 `<列表 UUID>/<短键>`。最小规则集、`rule` 命令都用这种形式；命令行也接受列表 UUID 的唯一前缀。
- **不发给模型：** 槽位决定位置和优先级，不作身份；UUID 和短键都不发给业务模型。选择请求中的候选用临时短键 `c1`、`c2`……（3.3）。
- `name` 是供人阅读的元数据，不作身份。

RuleList（一个 YAML 文件一个列表）：

| 字段 | 必填 | 说明 |
|---|---|---|
| `schemaVersion` | 是 | `"2"` |
| `id` | 是 | 完整 UUID |
| `title` | 是 | 多语言文本 |
| `slot` | 是 | 8 位十六进制，决定位置和优先级 |
| `version`、`ctime`、`mtime`、`digest` | 是 | 由 `rule` 命令维护 |
| `references` | 否 | `[{ ruleListId: <完整 UUID>, version }]` |
| `applicability` | 否 | 只用于可以被检索的段（Debug、业务）。只能绑定的段不写，由绑定计算负责（O-4） |
| `rules` | 是 | 按作者顺序排列，渲染编号即按此顺序 |

Rule（嵌在列表中）：

| 字段 | 必填 | 说明 |
|---|---|---|
| `id` | 是 | 完整 UUID；短键为其前 8 位 |
| `name` | 是 | 供人阅读的短名（kebab-case），渲染时显示，不作身份 |
| `version`、`ctime`、`mtime`、`digest` | 是 | 由 `rule` 命令维护 |
| `level` | 是 | 五个级别之一（6.1） |
| `description` | 是 | 多语言，写"适用于什么情况、约束什么"；向量检索和无向量选择都用它 |
| `instruction` | 是 | 多语言正文 |
| `applicability` | 否 | 只在需要比所在列表更窄时写 |
| `conflicts` | 否 | Q3 冲突键 |

去掉的字段：

| 字段 | 原因 |
|---|---|
| `category` | 由槽位段推导（O-1）：基础段为 general，语言与代码规范段为 general，框架段为 framework，判定段为 scenario，业务段为 business |
| `retrievalDescription` | 并入 `description` |
| 只能绑定段的 `applicability` | 与绑定计算重复（O-4） |
| 空的默认值（`references: []`、`conflicts: []` 等） | 不再写出 |

**多语言文本（R-11）：** 是一个以语言为键的映射，键取配置支持的语言（现在是 `en`、`zh`）。编译器 Rule 必须覆盖全部支持的语言；以后新增语言时，补齐对应变体即可。运行时按 `config.locale` 选择，选中的语言固定在快照中（D-18）。

**本地差异层**修改的是同一 UUID 的 Rule，不产生新身份。0.5 的项目业务 Rule 使用各自新生成的 UUID。

### 4.2 摘要与版本规则

- **Rule 摘要范围：** `id`、`name`、`level`、`description` 与 `instruction` 的全部语言变体、`applicability`、`conflicts`。不含版本、时间和摘要本身。
- **列表摘要范围：** `id`、`title`、`slot`、`references`、`applicability`，加按作者顺序排列的各 Rule 的版本号和内容摘要。
  （实施中修正：Rule 版本号不在内容摘要里，若列表摘要只含内容摘要，单独修改某条 Rule 的版本号时安装清单无法发现。）
- **加载时：** 重新计算摘要，与 YAML 中记录的不一致即拒绝加载。
- **安装清单：** 由 `rule` 命令生成，内容为列表 UUID、路径、版本、槽位、摘要，编译进程序（O-10）。
- **内容变化必须升版本：** 清单中的摘要变了而版本没变时，以独立的错误原因报告。

### 4.3 `rule` 子命令（R-7）

挂在现有的 `xcompiler` 命令下，`xcompiler rule --help` 列出全部操作：

| 子命令 | 作用 |
|---|---|
| `rule ls` | 列出 RuleList：槽位、名称、版本、条数 |
| `rule show <列表或 Rule>` | 显示定义与元数据 |
| `rule add` | 在列表中新增 Rule |
| `rule update` | 修改 Rule 或列表的字段 |
| `rule rm` | 删除 Rule。**当前置空**：只提示功能无效，退出码 1，不做任何修改（见 3.2 末尾） |
| `rule create-list` | 新建 RuleList（槽位必须在允许的段内且未被占用） |
| `rule discard <列表>` | 丢弃某个列表的本地差异，用于处理升级后待审的差异（实施中补充） |
| `rule check` | 全量校验：结构、摘要、版本、槽位、引用、安装清单一致性；有待审差异时以退出码 2 结束 |
| `rule export` | 把所有本地差异导出为一份 YAML，供审阅和更新到主仓库 |
| `rule promote` | 只在源码仓库可用：把已生效的差异写入 `rules/` 并重新生成清单 |
| `rule render` | 按指定的角色、工作、语言预览实际发给模型的 Rule 块（只读，便于审阅） |

- 写操作自动维护 `ctime`、`mtime`、`digest`；内容变化而版本号未升时拒绝写入；写完重新生成编译进代码的安装清单。
- 通过结构化解析读写 YAML，保留作者注释和顺序，不做文本替换。2026-10-20 实施（RC-05、RC-06）：
  - `promote` 把每条注释留在它所注释的字段或 Rule 上（Rule 按 id 对应），写出的内容必须与规范内容一致，否则拒绝；
  - `promote` 整批处理：先算出全部发布版本，把指向同批本地版本的列表引用改为发布版本，校验发布后的完整目录，写入后重新加载并核对摘要，全部通过才删除差异；同批两个新列表同名时各得一个文件。
- 错误使用类型化错误码，并写明下一步该怎么做。
- **适用范围的编辑（2026-10-20 实施）：** `rule add`、`rule update`、`rule create-list` 接受可重复的 `--scope <维度>=<值>`（维度为 11.4 的登记名，如 `--scope paths=tests/** --scope intents=greenfield`），同一维度的多个值合并；`rule update --clear-scope` 清除条目的适用范围。受保护段（创世、基础）的条目和只能绑定的段的列表不接受适用范围，由 schema 拒绝并给出类型化错误。

### 4.4 基础层与本地差异层（R-9）

| 层 | 位置 | 可写 | 说明 |
|---|---|---|---|
| 基础层 | 安装包中的 `rules/`，由编译进程序的清单校验 | 否（只能在源码仓库中修改） | 与现在相同 |
| 本地差异层 | `<XC_PATH 或 ~/.xc>/rules-local/`，可用 `XC_RULES_LOCAL` 覆盖（实施中确定：避开 `rules/`，因为 `XC_PATH` 可能指向安装根目录） | 是，由 `rule add/update/rm/create-list` 写入 | 每个列表一个文件，只记录相对基础层的差异 |

- **差异记录：** 每条记录写明它针对的基础列表 UUID、版本和摘要，以及新增或修改的内容（删除暂不支持，见 3.2 末尾）；带自己的 ctime、mtime 和 digest。
- **生效内容：** 基础层叠加差异层。修改过的 Rule 和列表使用本地版本号，例如 `1.0.0+local.1`，摘要随内容重新计算。
- **快照与审计：** 记录实际生效的内容，以及来源（基础版本和摘要、差异记录的摘要），与现有 Q5 一致。2026-10-20 补齐（Codex 审计 RC-04）：本地来源记录差异的修订号和摘要，修改发布列表的差异另记基础版本和摘要；这些证据在快照中，差异文件之后被修改、丢弃或写回都不影响追溯。
- **基础层升级：** 例如安装了新版 XCompiler。差异记录针对的基础摘要不再匹配时，不自动套用，而是标记为待审，并由 `rule check` 报告。参照 Debug Wiki 的 `needs_review`。2026-10-20 补齐（RC-02，用户确认）：
  - 新版基础层占用了本地新建列表的槽位时，以基础层为准，本地列表待审（`slot_taken`）；两个本地列表占同一槽位时都待审，不替用户选择；`create-list` 不再分配待审本地列表占着的槽位。
  - 差异文件损坏（无法解析或校验失败）时，请求拒绝运行，避免在用户不知情时丢掉其修改；`rule check` 把它列为无效文件（退出码 1）并给出 `rule discard <UUID>`；`discard` 只按文件名工作，所以在这两种状态下都能用。
- **更新到主仓库：** `rule export` 把差异导出为可审阅的变更。在源码仓库中执行 `rule promote` 时，把差异写入 `rules/`、升级版本、重新生成清单，并清除已合入的差异。
- **业务 Rule（0.5）：** 写入项目自己的目录，使用同一组子命令。

### 5.1 槽位（R-6，修改合同 1.8）

地址空间扩展为 32 位，当前只使用 `0x00000000`～`0x000FFFFF`。各段的先后顺序与现在相同，所以跨段优先级不变；每段都留出充足的增长空间。

| 槽位 | 用途 | 现有列表的新位置 |
|---|---|---|
| `0x00000000` | 创世声明 | 原 `0x0000` |

| `0x00001000` | 普通未分配槽位（O-2 取消索引块） | 原语言索引 `0x0100` |
| `0x00001001`–`0x00001FFF` | 语言契约 | TypeScript `0x00001001`，Python `0x00001002`（新增） |
| `0x00002001`–`0x00002FFF` | 代码规范（语言槽位 + `0x1000`） | TypeScript `0x00002001`，Python `0x00002002`（均新增） |
| `0x00003000`–`0x0000FFFF` | 语言段其余，保留 | |
| `0x00010000` | 普通未分配槽位（O-2） | 原框架索引 `0x0200` |
| `0x00010001`–`0x00010FFF` | 角色段 | 8 个角色 `0x00010001`–`0x00010008` |
| `0x00011000`–`0x000110FF` | 工作段：共享与模式片段 | 执行通用、基线延后、修 Bug、改 CR：`0x00011000`–`0x00011003` |
| `0x00011100`–`0x000111FF` | 工作段：Step 工作 | 8 个 Step 工作 `0x00011100`–`0x00011107` |

| `0x00012000`–`0x0001FFFF` | 其他框架列表 | |
| `0x00020000`–`0x0007FFFF` | Debug 段 | 原 `0x0300`–`0x0FFF`，仍为空 |

- 语言契约的槽位号小于代码规范：两者冲突时，构建、测试、导入等契约优先于风格规范。

- YAML 与渲染统一写成 8 位十六进制（如 `0x00001001`）；解析仍接受数字和不同的大小写，按数值比较。

## 6. 渲染与级别

### 6.1 级别定义（R-8）

级别定义写成 RuleList，放在基础段 `0x00000001`，en/zh 两版。基础段每次业务请求和 Rule 选择请求都加载。
LLM 接口没有会话状态，所谓"项目初始化时设置背景"就是每个请求都带上这一段；它排在所有业务 Rule 之前。

定义（用户已确认）：

| 级别 | 含义 | 约束程度 |
|---|---|---|
| `mandatory` | 强制：框架或语言层面的硬约束 | 任何情况下都必须遵守，违反即视为输出无效 |
| `forbidden` | 禁止：不得采取的做法 | 与 `mandatory` 相同 |
| `required` | 业务必须：完成本次工作或满足项目业务所必须达成的要求 | 必须满足；与 `mandatory`/`forbidden` 冲突时让位，并在输出中说明冲突 |
| `advised` | 建议：推荐做法 | 有充分理由可以不采用，但要在输出中说明理由 |
| `announce` | 声明：背景信息 | 不构成指令，不授予任何权限 |

- 级别表示单条 Rule 的**遵守程度**。不同列表之间的冲突仍按槽位裁决（原合同：级别不构成单独的数值优先级）。
- 级别定义中写明：`mandatory` 与 `forbidden` 级规则覆盖 Step 描述中与之相反的内容。原 TypeScript 列表第一条元规则随之删除（O-5）。
- 创世声明仍只能是 `announce`。级别定义本身是 `announce`：它说明规则怎么读，不是对任务的指令。

### 6.2 产出语言（R-11）

- 基础段 `0x00000002` 放一条"产出语言"规则，每种支持的语言各一个变体，变体本身就写明该语言。例如：
  - en：所有自然语言产出（文档、报告、说明、提交信息）使用英文，除非已接受的需求另有规定；
  - zh：所有自然语言产出使用中文，除非已接受的需求另有规定。
- 由 `config.locale` 选择变体，所以配置语言直接决定模型的产出语言；以后新增语言时补一个变体即可。
- 目前散在各提示中的"文档语言跟随当前 i18n 语言"等说法删除，以这条规则为唯一来源。
- i18n 继续保留：CLI 文本、提示模板（协议、JSON 格式等框架材料）仍由 i18n 按 `config.locale` 提供。

### 6.3 渲染格式

- 按列表分组。组标题为 `[槽位] 列表标题 (v列表版本)`，每个列表只写一次。
- 组内按作者顺序编号，每条都附上级别及其约束程度，例如：

  ```text
  [0x00001001] TypeScript runtime and test contract (v2.0.0)
  1. [mandatory · 强制] vitest-only: Tests use Vitest ...
  2. [required · 业务必须] ...
  ```

- 文字引用（如"第一条声明"）按编号对得上。
- 不再发送 Rule ID、列表 ID 和各条版本，它们只保存在快照与审计中。
- 业务请求提示模板版本 `rule-business-request/1` → `/2`。旧请求保留自己的版本号和请求摘要，恢复不重新渲染，不受影响。

实施中确定的细节（2026-10-19，第 6 步）：
- **编号取作者顺序中的位置**（位置 + 1），所以同一条规则在任何请求中编号都一样。本次请求没有带上的条目（例如代码 Step 未选中的项目配置条目）留下空号，例如 TypeScript 组显示 1、6、7、8。
- **结构不可伪造：** 只有组标题和规则行顶格；指令正文的后续行一律缩进 4 个空格，标题中的换行合并为一行。正文里即使写了 `[0x…]` 或 `1. [...]` 也只会出现在缩进行中。原先用 JSON 包住正文是为了同一目的，改为纯文本后由这条规则保证。
- **开头的框架说明与级别含义按请求语言渲染**（i18n `ruleBlock`，按快照中的 locale 显式取，不用进程当前语言），同一快照恢复后渲染结果不变。
- 快照的已考虑条目新增列表标题与条目位置，渲染内容（名称、标题、编号）都与之核对。
- 级别定义列表 7 条，全部为 `announce`：总述、五个级别各一条、"`mandatory`/`forbidden` 覆盖 Step 中相反描述"。O-5 因此在本步完成，TypeScript 元规则已删除，最小规则集随之去掉该条。
- 产出语言条目级别为 `required`。原执行提示中"按当前 i18n 语言写文档包"的说法已删除。
- 发布清单 `scripts/package.sh` 加入两个基础段文件。

## 11. Rule 规范与流程（2026-10-19 用户确认）

0.4 的目标是集成 Rule 功能：内容按最小集使用，但规范和流程要定下来，便于后续扩展。本节是 Rule 的使用场景、选择机制、编写和来源的规范；与前文冲突时以本节为准。

### 11.1 使用场景

| 请求 | 带的 Rule | 说明 |
|---|---|---|
| Step 执行（各 Step 工作、修 Bug、改 CR） | 基础段 + 语言（最小规则集）+ 角色 + 工作片段 + Step 工作 + 经引用的列表 | 每次执行选一次，各轮复用快照（D-6） |
| 需求澄清、阶段规划 | 基础段 + 角色 | 不绑定语言列表 |
| 阶段拆解 | 基础段 + 语言（`projectSetup`）+ 角色 | 不跟随引用 |
| 场景结果判定 | 基础段 + 角色 + 判定评分规则 | 不做任何相关性选择 |
| 相关性选择评审 | 基础段 | 只用于读懂规则，不含业务规则 |
| 协议纠正 | 无 | 固定协议模板（D-3） |
| 插件发起的模型调用 | 无 | 插件自行负责 |

基础段（创世、级别定义、产出语言）是每个业务请求和选择评审请求的固定前缀。

### 11.2 选择策略

相关性选择只作用于开放段（3.5）。语言、角色、工作列表的条目只作为必需条目进入请求，由最小规则集和适用维度决定（11.4）。

| 策略 | 做法 | 额外调用 | 0.4 |
|---|---|---|---|
| `bound-only` | 不做相关性选择，只带必需条目 | 无 | 实现，默认 |
| `inline` | 适用的可选条目连同"何时适用"一起放进业务请求，由执行模型自行取舍 | 无 | 0.5 |
| `embedding` | 向量排序，低分交本角色模型评审（Q4 C） | embedding；低分时一次对话 | 机制已实现，配置暂不开放 |
| `review` | 全部候选摘要交本角色模型选择 | 一次对话 | 机制已实现，配置暂不开放 |

实际采用的策略由三层决定，每层只能收窄：
1. **代码按工作限定可用策略**（`RULE_SELECTION_POLICY`）：场景结果判定只允许 `bound-only`，其余工作允许全部策略。
2. **用户配置默认策略和预算**：`rules.selection.strategy`（0.4 只接受 `bound-only`），候选上限沿用 `rules.retrieval.max_candidates`。
3. **运行时降级**：候选超过上限、向量检索失败、评审失败时，本次请求降为只带必需条目（11.3）。

快照记录本次的策略和是否降级；恢复时不重新决定。

**选择用的任务摘要（2026-10-20 实施）：** 相关性选择（向量与评审）只看任务摘要和错误摘要，不看完整的业务请求。各请求的来源：

| 请求 | 任务摘要 | 错误摘要 |
|---|---|---|
| Step 执行 | Step 描述 | Debug 简报的原因（修复时） |
| 需求澄清、阶段规划、阶段拆解 | 原始需求 | 无 |
| 场景结果判定 | 场景预期 | 无 |

两者先去掉首尾空白，再按码点截到 `RULE_QUERY_SUMMARY_LIMIT = 2000` 个字符（`ruleSelectionQuery`），截断后为空的错误摘要不记录。快照和草稿的 schema 按同一上限校验。完整需求仍只出现在业务请求中。

### 11.3 失败降级

可选条目的选择不得阻断业务请求：
- 向量检索失败、评审失败（包括认领已消耗但没有结果）、候选超过上限时，本次请求只带必需条目继续。
- 快照的排序记录 `fallback`，原因用类型化代码：`retrieval_failed`、`review_failed`、`too_many_candidates`。审计保留原始错误。
- 降级后的快照照常固定，同一执行后续各轮复用，不再尝试选择。
- 必需条目本身的问题（缺失、版本不符、显式要求却不适用）仍然报错：那是绑定或目录的错误，不是选择失败。

实施中确定的细节：
- **只有"选择服务本身失败"才降级**：
  - 向量服务失败或返回无效向量；
  - 评审回答无法使用（`invalid_output`、`response_evidence_invalid`）；
  - 评审的模型调用失败；
  - 候选超过上限。
- **完整性问题照常报错，不吸收**：回放未命中、缺少审计、本地索引或状态损坏、评审结果绑定到别的请求、配置错误、无类型的异常（缺陷）。
- **认领已消耗却没有结果时**：
  - 进程中断或取消：下一次进入同一请求时降级为 `review_failed`，原因记为 `rule_request_failed/review_incomplete`；
  - 上次以完整性错误结束：2026-10-20 起（Codex 审计第 4.1 节，用户确认）该错误按类型码记入不可变的评审失败记录，重试时以 `rule_request_failed/review_failed` 再次报出原始原因，不降级。请求标识是每次执行一个，所以只阻止该次执行的后续轮次，下一次执行重新选择。
- 哪些评审失败可以降级由评审端口自己判断（`failureOf`），协调器不认识具体的模型错误类型。
- 同一请求如果先后发布了两个结果（例如等待中的调用方先发布了降级结果），以先发布的为准，后到的调用方直接返回它。
- 快照中 `ranking.mode`（`vector`、`summary`）改名为 `ranking.strategy`（`embedding`、`review`，新增 `bound-only`），配置、代码和证据用同一套名称。

### 11.4 适用维度

每条 Rule 和每个列表可以声明适用范围。同一维度内满足其一即可，不同维度之间必须同时满足。

| 维度 | 含义 | 匹配 | 上下文来源 |
|---|---|---|---|
| `projectIds` | 项目 | UUID，忽略大小写 | 所有业务请求 |
| `languages` | 项目语言 | 精确 | 带语言的请求 |
| `roles` | 角色 | 精确 | 所有业务请求 |
| `works` | 工作 | 精确 | 所有业务请求 |
| `intents` | 项目模式：`greenfield`、`feature`、`refactor`、`self` | 精确 | 规划请求、Step 执行 |
| `projectTypes` | 项目类型：`application`、`library`、`mixed` | 精确 | Step 执行 |
| `tools` | 本次可用的工具 | 声明的工具中有一个可用 | Step 执行 |
| `paths` | 本次请求可写入的路径（上下文字段 `writablePaths`）：Step 声明的产出，以及 Runtime 授予的写入目录（以 `/` 结尾，例如验证 Step 的补充测试目录、fixture 目录） | 文件按路径模式匹配（`*` 不跨目录，`**` 跨目录，`?` 单个字符）；目录在其下有文件可能匹配时算匹配；通配写法按字面目录前缀判断，只会多带、不会漏带 | Step 执行 |
| `failureCategories` | 本次修复的失败类别（与 Debug 简报同一组类别） | 精确 | 修 Bug 的 Step 执行 |

- **缺少上下文**（例如规划请求没有工具和产出）：声明了该维度的条目跳过；调用方显式要求的条目报 `required_inapplicable`。
- **绑定列表也按维度过滤**：最小规则集表示"这类工作可以携带的条目"，不适用的跳过，不报错；被引用列表同样处理。基础段不按维度过滤，基础段条目不得声明适用范围。
- **考虑过、暂不加的维度**：Step 种类（已由 `works` 覆盖）、Phase 序号、项目依赖或框架（需要读取清单，留给 0.5 的业务规则）、运行平台与沙箱模式、产出语言（Rule 本身已按语言提供变体）。
- **上下文取值**：`tools` 取本次请求实际提供给模型的工具；`writablePaths` 取 Step 声明的产出加上执行器的写入许可（2026-10-20 起，Codex 审计 RC-01，用户确认：原来只取声明的产出，验证 Step 只声明报告，补写测试时拿不到测试规则）；`failureCategory` 取 Debug 简报的类别（修复重试时取最新一次失败的简报）；`intent`、`projectType` 取计划。全部来自保留的请求载荷，恢复时读到的相同。
- **TypeScript 列表的维度**（第 11 节实施）：

  | 条目 | 维度 |
  |---|---|
  | 配置归属 | `intents: [greenfield]`（正文只针对 greenfield） |
  | 只用 Vitest、时间冻结 | `paths`：测试文件 |
  | 本地导入 `.ts` | `paths`：TypeScript 文件 |
  | `package.json` 脚本、tsconfig 范围、测试文件命名、开发依赖 | 不加：拆解也需要它们，而拆解请求没有产出和工具 |

  例如只输出文档的详细设计 Step 不再带测试和导入规则；feature 模式不带配置归属。
- **扩展方式**：维度在一张登记表中定义（名称、取值、上下文字段、匹配方式），schema、匹配和校验都从登记表生成；新增维度只需登记并让请求提供对应上下文，类型检查会要求补齐匹配方式。

### 11.5 Rule 编写规范

- **字段**：见 4.1。`name` 用 kebab-case，说明这条规则是什么；`instruction` 是发给模型的正文，两种语言都要写。
- **description**：写"何时适用 + 约束什么"，英文以 `Applies when` 或 `Applies to` 开头，中文写明"…时适用"或"适用于…"。开放段的条目由 description 参与相关性选择，必须符合；绑定段的条目建议符合。`rule check` 对不符合的开放段条目给出警告。
- **级别**：见 6.1。级别约束模型的遵守程度，不做机械检查；需要机械保证的约束应同时由门禁验证。
- **适用范围**：能由维度确定的适用性用维度表达，不交给相关性选择。规划也需要的规则不要声明 `tools`、`paths`、`projectTypes` 这类只有 Step 执行才有的维度，否则规划请求会跳过它。
- **冲突**：两条规则对同一事项给出不同要求时，用冲突键声明（Q3），按槽位裁决；同一列表内不得冲突。

### 11.6 来源与审核

| 来源 | 位置 | 审核与发布 |
|---|---|---|
| 编译器规则 | 源码仓库 `rules/`，安装清单校验 | 改动随版本发布；内容改动必须升版本 |
| 本地差异 | `<XC_PATH 或 ~/.xc>/rules-local` | `rule add/update` 写入；`rule export` 导出审阅；`rule promote` 在源码仓库合入。删除暂不支持（3.2） |
| 项目规则（业务段） | 项目自己的目录 | 0.5 |
| Debug Wiki 转化（Debug 段） | 由 Wiki 条目整理成规则 | 0.5：转化、审阅、版本规则待定；类别对应 `failureCategories` |

### 11.7 校验

`rule check` 依次检查：
1. 结构、摘要、版本、槽位、引用、安装清单（已有）。
2. 本地差异：已生效或待审（已有）。
3. **绑定能否解析**：对每种角色、工作、Step 工作、语言、基线延后组合跑一遍绑定，报告缺失的列表和最小规则集中缺失的短键。
4. **description 写法**：开放段条目不符合 11.5 时警告。
