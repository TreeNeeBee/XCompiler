## 1. Rule 的维护和生效方式——优化后的 B 已确认

问题是派生工程的业务 Rule 由谁写入，以及哪些规则必须随请求加载；不是重新选择 RuleList 槽位数量。
用户先询问两种方式的影响，随后明确选择下述优化后的 B。

| 方案 | 行为 | 影响 |
|---|---|---|
| A，人工维护，此前的首版建议，未选择 | 人工维护派生工程范围内的 YAML，并显式绑定/引用已有共享 Rule | 写入和生效时机清楚，实现较简单；需求变更后需要同步维护业务规则 |
| B，已选择下述受控版本 | 由现有 build/run 中负责已接受需求及变更的流程生成或更新项目业务 Rule | 自动化程度更高；候选限域、随正式交付生效，保留来源和版本恢复证据 |

人工维护的具体工作是：把需要反复遵守的稳定项目约束写成 YAML Rule，说明规则正文、专用检索描述、
适用范围、来源和共享规则引用；需求发生相关变化时同步修改业务 Rule 并更新版本。
不是把每条需求、临时任务或全部设计文档再抄成 Rule。结构校验、生成索引、哈希与文件组织由工程实现，
已选择的第 2 项 A 会处理向量索引的按需构建/重建，人工不需要维护向量内容。

B 的主要风险是：从需求中提炼错约束；需求文档与 Rule 出现两个互不一致的权威版本；
尚未完成的变更提前影响其他请求；失败、恢复或并发修改时无法确定哪一版正式生效。
这些风险需要与现有计划/CR 流程协调，不能靠多加一段提示解决。

当前流程也不是统一的人工审核门：build 交互模式有两次确认，但 `--yes` 可跳过，正式计划在第二个门之后保存；
run 的合同 CR 没有普遍的人工确认门，创建即进入活动流程，CR 完成处理也早于候选工作树合入权威工程。
因此不能宣称 B 可以直接复用一个已有的、覆盖所有路径的人工批准步骤。

结合 build/run 的自动化目标，已确认采用以下**受控 B 合同**：

- 业务 Rule 先作为候选随原计划/CR 在其所属范围内使用，不立即覆盖整个派生工程的正式规则。
- build 的正式计划持久化及 Project 绑定成功后，初始业务规则才正式生效。
- CR 对应质量检查通过并合入权威工程后，才更新正式业务 Rule。
- 失败或待权限时保留旧正式版本，并让候选随原计划/CR 恢复；不增加逐条 Rule 的独立人工确认门。
- 新正式版本只用于新的逻辑请求；旧请求继续遵循 Q5 已固定的内容与版本。

自动维护的边界已经选定，具体候选存储、生成、校验和激活接线仍需实施；不得把选择记录当成已上线。

两者均不能修改受保护基础规则或发布版 Debug Rule，也不能把项目专用内容自动提升为共享规则。
共享 Rule 通过引用复用，不因项目绑定而产生可独立修改的共享副本。

基础规则按已确认合同加载；第 3 项 A 也确认已确定的必需规则不受相似度阈值或可选候选上限裁剪。
非基础规则的必需绑定来自所接受的计划/变更及明确框架绑定，不能由相似度或指令等级猜测。

采用的生效合同：

- 非基础规则显式区分“当前请求必需绑定”和“可选检索”。
- Rule 的声明等级描述指令强度，不自动决定召回或新增执行门禁；必需性由加载合同决定，冲突优先级仍由槽位决定。
- 语言、角色、场景、项目等限定维度之间取 AND；同一维度的允许值取 ANY；未声明限定表示不限制该维度。
- 普通可选规则在缺少必要上下文时不视为匹配；显式必需绑定如果无法确认适用性、内容缺失或存在无法按 Q3 解决的冲突，必须明确失败，不能静默丢弃。可按 Q3 解决的跨列表冲突仍保留低槽位规则和覆盖证据。

上述生效语义随本组方案落实；字段名称和序列化方式由实现负责。

## 2. 向量输入与索引生成时机——A 已确认

| 方案 | 行为 | 影响 |
|---|---|---|
| A，已选择 | 显式配置 embedding 服务；运行时按需构建或重建本地版本化索引，后续复用 | 首次使用或规则/模型变更时有构建耗时和模型调用成本，日常维护较直接 |
| B，未选择，保留作历史比较 | 运行时仅消费预先生成的兼容索引；缺失或过期时明确停止 | 构建成本前移，但发布/安装流程必须额外提供匹配索引 |

**B 仍需为当前查询调用 embedding；预生成规则向量不等于运行时不调用模型。**

采用以下输入边界：索引编码 Rule 的专用检索描述；查询编码当前任务/错误摘要及结构化上下文。
不自动发送整个派生工程、Wiki 或原始审计。embedding 是向量接口，不组装聊天提示；
基础规则加载适用于后续业务和规则复核聊天请求，不把整段基础规则拼入向量输入。
实际端点、模型和凭据由配置明确提供，不根据模型名称猜测能力，也不预置隐式备用向量空间。

索引身份绑定规则内容/检索描述版本、输入表示版本、模型身份和向量维度；变更后不能复用不兼容索引。
格式、哈希和本地文件组织属于工程实现；新旧索引或历史请求证据的自动删除不在本方案内。
本次选择批准产品行为设计，不代表在本仓库开发会话中立即调用外部模型。

## 3. 检索阈值、候选上限和低分结果——A 已确认

已确认的首版配置是：`score = (cosine + 1) / 2`，阈值 `0.8`，相等时通过，最多 `20` 条可选候选。
**这些是已选择的初始配置，尚未校准或验证，不代表已证明的检索质量。**

| 方案 | 低分复核明确判定无匹配时 | 影响 |
|---|---|---|
| A，已选择 | 使用已确定的必需规则继续当前请求 | 可选规则库稀疏时仍能工作；可能缺少可复用的补充指导 |
| B，未选择，保留作历史比较 | 暂停当前请求，要求补充规则或明确解决该选择结果 | 对无匹配采取更严格处置；普通任务也可能因可选规则不足而中断 |

已确认的检索合同：

1. 先判断适用性，必需规则单独保留，再从可选规则中取相似度最高的候选；同分时用稳定身份排序。
2. 候选中存在分数达到阈值的规则时直接采用这些规则。没有达到阈值但仍有候选时，最多发起一次逻辑选择复核。
3. 复核使用当前调用方已有角色的配置模型池，只能从给定候选 ID 中选取，不新增角色、不扩张适用范围、不输出业务判决。
4. 空可选候选集按无匹配处理，不发起没有候选的复核。缺失必需规则仍是错误。
5. 向量服务失败、索引损坏或复核失败与“明确无匹配”严格区分；不得静默使用词面检索、切换向量空间或当成无匹配继续。
6. 这次逻辑选择复核的计数与 Q6 协议校准分离，网络重试或提供方切换不能重建逻辑额度。

候选上限只约束可选召回，不截断基础规则和必需内容，也不允许在模型容量不足时静默丢弃它们。
参数应由带结构校验的配置承载；其批准不等于已经测得效果，不能在统一验证前宣称已校准。
业务 Rule 的写入权与非基础规则的必需绑定来源依第 1 项受控 B 实施。

## 4. 协议校准允许哪些无损变换——B 范围方向已确认

原生产模型和一次逻辑额度已经确定。本项只选择可修复的表示范围。

| 方案 | 允许范围 | 影响 |
|---|---|---|
| A，较窄方案未选择 | 已知完整外层代码围栏/包装的移除，以及字符串外可机械识别的尾随逗号；修复结果必须证明保留原有值 | 可验证边界清楚；更复杂的语法错误可能仍需原业务流程重新生成 |
| B，已选择 | 在 A 之外增加逐项定义并可机械证明值不变的引号、转义等修复 | 覆盖更多错误；需要更复杂的解析和保持性证据，无法证明时仍不能接受 |

A 的窄范围只是 B 的基础，不能把已选择的 B 缩回只处理包装与尾随逗号。
已知可确定性处理的情况仍使用最窄路径；引号、转义等扩展修复必须按真实错误样例逐类定义并证明。
第一批白名单和证据见 [协议校准合同](output-calibration.md)，其余类别仍待实现；选择 B 不表示所有缺失引号、转义错误都可无损恢复。
无法证明原值的样例必须保持未解决，不能为了扩大覆盖而猜测字段、边界或值。
