## Confirmed structure

- A Rule expresses an instruction or a judgement contract. A RuleList groups Rules by function.
- RuleChain is the global catalogue organizing RuleLists. Consumers find the applicable RuleLists
  through it; it is not the rule subset assembled for one model call.
- RuleLists may reference other RuleLists. A per-call selection record is distinct from RuleChain.
  Its schema remains open; reference loading follows confirmed Q3 below.
- Global UUIDs identify objects. A RuleList's numeric slot locates it in RuleChain and determines
  its priority; UUID order does not establish priority.
- A RuleList occupies one slot. The 2026-09-07 clarification closes the earlier cardinality question;
  multiple-slot mounting is not part of this model. A RuleList supports lookup of individual Rules,
  so selecting a relevant Rule does not imply forwarding every Rule in its list. This does not
  weaken the separately confirmed mandatory base-loading contract.
- RuleSelector selects the related Rules. RuleDecorator aggregates the effective selection with
  its owning-list metadata for the framework's prompt generation. The framework still owns current
  request messages, evidence, final request integrity and provider dispatch.

The previous proposal defining RuleChain as a context-specific ordered list is superseded. This
decision does not require a linked list, blockchain consensus, or a second lifecycle store.

## Functional categories and project scope

The user clarified four categories on 2026-09-07:

| Category | Responsibility | Example |
|---|---|---|
| General | Reusable development and language constraints | General development conventions, TypeScript/Python instructions |
| Framework | Normal operation of XCompiler's overall framework | V-model, Ticket and Step workflow instructions |
| Scenario | The standard for a specific compiler operation or decision | Bug versus CR classification against the current accepted contract |
| Business | Rules specific to a generated project, including its special requirements | An accepted project-specific output or integration contract |

These categories describe purpose. Slot numbers still determine priority, and applicability still
determines which Rules concern a request. General does not mean always loaded: the confirmed base
loading rule is separate, and a Python-only instruction must not reach a TypeScript-only request.
Framework Rules describe how actors participate in the workflow; deterministic lifecycle, gate and
permission enforcement remains in code. Scenario Rules are reusable judgement standards, not
historical case verdicts. Business Rules apply only within their accepted project scope.

A reusable business rule may be extracted into a scenario or framework rule after its
project-specific assumptions are removed. This is a change to the authoritative standard, not an
automatic consequence of a high similarity score. The exact authoring/review and project-binding
record remains to be specified; no Runtime promotion API has been approved.

Recommendation for detailed design: model category independently from slot, retaining the confirmed
slot allocations. The existing language/framework/business range indexes need not be identical to
the four purpose categories. No new scenario range or index has been assigned by this clarification.
Q5 A now requires per-request retention of the actual selected content, versions and retrieval
evidence. Physical storage, deduplication and any full-catalogue archive remain detailed storage
choices, separate from the settled one-slot RuleList structure.

### Debug capacity and growth

The user-authorized enlargement uses all contiguous framework space from `0x0300` through `0x0FFF`,
replacing the proposed `0x0300-0x03FF` segment. This provides thirteen times as many lists while
retaining the role slots, business index and cross-range precedence. It leaves 249 ordinary
framework slots at `0x0207-0x02FF`. Every Debug slot is a list location, including `0x0300`; there is
no new Debug index slot and the segment does not become mandatory base content.

A slot identifies a functional RuleList, not one Rule, one Bug or one Wiki entry. Each list may
contain many individually addressable Rules. Organize large collections with populated catalogue
entries and generated list/Rule indexes; subdividing lookup metadata does not allocate additional
slots or change Rule identity. Selector locates the applicable lists and Rules, and Decorator
aggregates only the effective selection for framework prompt generation. The confirmed base
loading and actual-provider capacity checks remain separate obligations.

Debug is a functional grouping within the four Rule categories. A framework repair procedure and
a specific diagnostic scenario retain their different applicability even when stored in this
segment. Large shared collections must not import derived-project-only assumptions.

The address space still ends at `0xFFFF`. If more than 3,328 Debug RuleLists become necessary,
address-width or range reallocation needs an explicit catalogue-version change. There is no
automatic spillover into business slots, composite per-Rule priority or silent renumbering.

The reserved base policy also covers slot zero. Q2 confirms that these definitions are treated like
source-controlled constants: Runtime, models, Plugins and generated projects cannot modify them or
automatically upgrade them. A maintainer must manually edit the engineering source and update its
version to change protected content. This supersedes the automatic/Runtime-managed release-upgrade
alternative; it does not authorize replacing content under an unchanged version. Old-version
retention and interrupted-attempt recovery require the detailed Q5 contract; its selected direction
is now per-request actual-content/version and retrieval-evidence retention.

Index blocks provide quick lookup and location of RuleLists in their respective ranges. An index
entry is not itself an instruction to load or evaluate its referenced RuleList. Q1 selects YAML as
the definition authority and generated, validated indexes rather than independently maintained
index content. Exact record schemas remain to be specified. The three index slots are outside the
always-loaded base range.

## YAML-to-prompt boundary

Load YAML with a structured parser and validate the resulting definitions before selection or
rendering. YAML is the authoring format; the complete source file is not prompt content.

- Author comments belong to the source file and do not enter a model prompt. Preserve `#`, quotes,
  code examples and line breaks when they are part of a parsed instruction string; do not strip
  comments with a text-matching replacement.
- Render an explicit set of validated instruction fields and the metadata needed to interpret
  them, including Rule identity, owning RuleList slot, declared level and version. Do not render
  arbitrary YAML properties, catalogue indexes or local file paths as instructions.
- Each rendered Rule carries its owning RuleList slot. This is the confirmed priority source,
  not a new per-Rule priority field.
- Keep current project evidence and Tool output separate from authoritative rule declarations;
  neither can manufacture a higher-priority Rule block by embedding similar text.
- Retain source provenance separately from rendered content. The exact effective-content identity,
  raw-file digest and comment-only change behavior belong to Q5, not the YAML-format choice.

For example, a YAML author comment above a multiline instruction is omitted. A Markdown heading
beginning with `#` inside that multiline instruction is preserved as instruction text.

## Confirmed priority and declaration boundary

Among applicable, conflicting RuleLists, the lower numeric slot wins. Slot `0x0000` has the highest
priority. Comparison uses RuleList slots, not UUIDs, textual hexadecimal sorting, retrieval order,
similarity scores, or a new per-Rule numeric priority field.

Priority does not make an otherwise inapplicable language or role RuleList applicable. It also does
not establish that a test passed or that evidence is correct. Q3 selects deterministic checks for
declared conflicts; file order and the last-loaded instruction are not tiebreakers.

Confirmed Q3 behavior:

1. Referenced lists retain their own slots and applicability. Referencing a list does not promote
   its priority or make otherwise inapplicable rules apply.
2. Missing references and cycles are loading errors. Contradictory structured declarations inside
   one list are errors because slot priority cannot resolve them.
3. Across applicable lists, resolve declared conflicting keys by lower numeric slot, and retain the
   overridden rule and the reason in selection evidence. This deterministic check does not claim
   to detect every contradiction in free-form natural language.
4. Present effective rules in ascending numeric slot order, highest priority first, with the slot
   visible on each rule. Equal-slot ordering never resolves a conflict.
5. Include a prompt declaration that lower slot numbers have higher priority. The declaration and
   ordering supplement programmatic resolution; they do not replace it or introduce an extra LLM
   conflict-review call.

The user's explicit ordering answer resolves the earlier high-first/low-first wording ambiguity.

The genesis text is `announce`: a declaration, not an executable safety, permission, or gate policy.
It cannot authorize filesystem/network access, override host/platform constraints, resist user
cancellation through self-preservation wording, or turn a failed gate into success. Rule priority
orders Rule instructions; it does not replace the existing deterministic capability boundaries.

## Selection and judgement direction

The requested Rule system is broader than prompt insertion. It must support semantic judgement
contracts such as Bug versus Change Request classification from accepted context and evidence.
Rule results go back to the owning application flow; Rules do not create Tickets or mutate state.

The selection direction uses a configurable similarity threshold on a normalized 0-1 scale.
**Confirmed in the 2026-09-05 continuation:** the direct-use path selects an applicable instruction
or judgement rubric. It never supplies a historical verdict as today's outcome. The owning
semantic judge uses the selected standard with current accepted context and current evidence.
For the existing scenario judge, this reuses its present business-judgement call instead of adding
another judgement layer.

**Q4 C confirmed on 2026-09-07:** use vector semantic retrieval plus low-score model review. This
requires an explicitly configured embedding capability and a versioned vector index. The earlier
local-scoring recommendation is superseded. Semantic candidates do not require shared query words;
do not copy a lexical-overlap filter or Wiki's weighted scoring into this path. Model/index identity
must prevent mixing incompatible vector spaces, and failures cannot silently select another scorer.
Vector input and low-score review messages are separate contracts; embedding is not an optional
method on every existing chat client. The subsequent 2026-09-10 choices confirm the following
contract, also recorded in the [remaining decision review](remaining-decisions.md):

- **Index/input, item 2 A:** an explicitly configured embedding service builds/rebuilds a local
  versioned index on demand; compatible vectors are reused. Indexed text is a Rule's retrieval
  description, and query input is bounded current task/error summary plus structured context.
  Embedding does not receive a chat prompt or the base-Rule block. Business and selection-review
  chat requests still load base Rules. Do not silently embed whole projects, Wiki or raw audit.
- **Index identity:** bind Rule/retrieval-description version, input-representation version, model
  identity and dimensions. A changed vector space cannot reuse an incompatible index. Provider,
  model and credentials are explicit configuration values; no implicit alternative space or
  historical-data deletion is approved.
- **Scoring, item 3 A:** use `score = (cosine + 1) / 2`, an inclusive `0.8` threshold and at most
  20 optional candidates. These are approved initial settings, not calibrated or verified quality.
  Determine applicability first; keep required Rules independently of optional ranking/caps and
  use stable identity to order equal-scoring candidates.
- **Review:** select qualifying candidates directly. If none qualifies but candidates exist, make
  at most one logical selection-review request using the current caller's configured role pool.
  It selects only supplied Rule IDs and does not expand applicability or return business verdicts.
  Transport retries and provider switching cannot replenish this allowance, separate from Q6.
- **No match:** continue with required Rules only when review explicitly finds no match or the
  optional candidate set is empty; the empty set does not trigger a review call. Missing required
  content, vector-service failure, index corruption and review failure remain errors, not no match.

Non-base required bindings come from accepted project/flow contracts under controlled 1 B, not
similarity or declaration level. See the [C implementation contract](implementation-plan.md#q4-c-selected-vector-semantic-retrieval-and-low-score-review)
for the connected delivery slice. This decision record does not claim it has been implemented.

Keep these distinct in the detailed design:
- Applicability: whether a RuleList concerns the current language, role, task, or decision point.
- Similarity: retrieval relevance, not proof that a previous outcome is valid now.
- Priority: conflict precedence by numeric slot.
- Mandatory loading: populated base slots are included independently of retrieval scores.
- Evaluation: a typed result with current evidence, separate from selecting an instruction.

The earlier shorthand "mandatory threshold=1 means pass" is not an executable contract. A maximum
threshold cannot by itself mean unconditional selection or successful evaluation. The confirmed
base-loading rule must not depend on that arithmetic. The threshold boundary is now confirmed;
non-base writing/binding and typed applicability follow selected optimized 1 B. Historical-verdict
reuse is excluded by the continuation decision above.

## Output protocol boundary

Rule evaluators returning structured replies use the shared output protocol after prompt assembly.
The protocol is not selected from RuleChain and does not inherit slot priority or similarity.
Calibration only makes an LLM response protocol-valid; it does not
interpret Rule applicability, similarity, conflict, evidence or verdict semantics. The caller runs
those business checks afterwards. Malformed output may use the approved calibration path; it cannot
default to a successful Rule result or a guessed Ticket type.

Correction calls use a fixed versioned protocol template, not mandatory base content or applicable
business RuleLists. This keeps the bootstrap nonrecursive: a selector's malformed output can be
corrected without asking RuleChain to select the corrector's own instructions. Q6 A uses the
original response's actual producing provider/model for at most one logical calibration attempt;
transport retries and fallback cannot reset the allowance. Selected item 4 B extends the repair
scope to individually defined quote/escape repairs with mechanical original-value preservation.
D05 still requires the actual whitelist/proof and accounting/integration implementation; the
selection does not approve guessing ambiguous values.
