## Scope decision: 2026-09-04

0.4.0 now focuses on the Rule system and module separation. Story/Task redesign, functional Stories,
and Epic/Story V+V development are assigned to the initial
[0.5.0 iteration plan](../0.5.0/0.5.0-functional-stories-and-v-plus-v.md).

This scope decision supersedes the earlier requirement to implement branch and carrier-Story changes
in Phase C. Preserve current execution and delivery behavior while separating responsibilities.
Do not remove `workKind`, independently schedule Tasks, replace the CR chain, add permanent dev,
or consolidate ChangeSet/MergeRequest as an incidental part of 0.4. Their redesign requires separate
approval; retaining current behavior is not a promise of 0.3 data-format compatibility.

## Confirmed goals

- Runtime remains the only business entry point for CLI, ACP, and future adapters.
- PM drives Project, Phase, and the eight-Step V model; registered objects remain authoritative.
- Move semantic judgements out of text matchers only through separately approved, typed,
  evidence-backed contracts; the inventory is not blanket approval to replace all heuristics.
- Keep mechanically verifiable facts, permissions, identity, and persistence integrity deterministic.
- Make flow, rule composition, and business ownership inspectable instead of scattering them across
  the execution loop.
- Preserve current Phase/Step gates, Ticket routing, assignments, and revision-bound integration
  while extracting reusable rules and clarifying module ownership.

## Approved rubric reuse: 2026-09-05 continuation

High similarity may directly select an applicable instruction or judgement standard. It cannot
supply a historical verdict as the result of today's work. The existing semantic owner evaluates
the current accepted requirement/design and current evidence using that standard.

For the scenario judge, move its existing rubric to the approved Rule source and reuse its existing
PM model call. Its typed pass/fail, Bug/CR and target-Step result continues through current validation
and PM intake. Do not introduce another business-judgement layer or let similarity waive a gate.
Malformed output remains a runtime judgement failure; the existing prompt's Bug/CODE preference
when evidence does not establish a contract change remains a separate, preserved semantic policy.

This choice primarily improves rule management and traceability. It does not promise fewer business
model calls, deterministic verdicts or sufficient evidence. Rule selection and calibration can add
latency and need separately recorded costs. Q4 now selects vector semantic retrieval plus low-score
review, with the input/index/normalization/threshold/limit contract subsequently selected in items
2 A/3 A. Actual provider/model values remain explicit configuration, and the initial settings are
uncalibrated. Q5 A requires actual Rule content/versions and retrieval evidence per request; exact
storage/recovery implementation must preserve existing proof responsibilities. Q0 in the
[implementation plan](implementation-plan.md)
is explicitly confirmed: calibration uses only a fixed versioned protocol template, without base
Rules or RuleChain selection.

The acceptance contract includes a highly similar historical failure whose current accepted premise
requires a different classification or target. The real current-evidence judge must execute, and
removing that call must fail the regression test. Deterministic checks, permission decisions,
structural Bug deduplication, Ticket lifecycle, test gates and merges retain their current owners.

## Concerns are not automatically physical layers

The three concerns remain useful:

| Concern | Responsibility |
|---|---|
| Flow | Legal transitions, scheduling conditions, suspension, and resumption |
| Rules | Instructions, applicability, evidence requirements, and validation outcomes |
| Business | Project, Phase, Step, Ticket, role, and ownership semantics |

They do not justify removing the existing Domain/Application/Infrastructure boundary. The confirmed
mapping is D01: Domain owns pure contracts and transitions; Application coordinates effects and PM
work; Infrastructure implements file, process, network, and Git ports; Runtime assembles them.
A generic flow helper must not become a second persisted state store.

## Phase A: split by responsibility, not by filename

The old table placed mixed modules into Domain wholesale. That would introduce outward dependencies
which [the architecture tests](../../../tests/architecture_dependencies.test.ts) explicitly forbid.
Read the call sites and split the pure portion from orchestration and I/O before moving it.

| Former Core area | Pure contracts/policy | Coordination and effects |
|---|---|---|
| `core/plan.ts`, `phase_plan.ts`, `incremental.ts` | Planning schemas, phase status rules, pure impact calculations in Domain | Loading, saving, compilation, and progression in Application/Infrastructure |
| `quality_gate.ts`, `architecture.ts`, `test_assets.ts` | Quality schemas, thresholds, path/ownership contracts | Workspace inspection and language-dependent execution remain outside Domain |
| `entry_gate.ts`, `paired_test_contract.ts` | Pure validation of supplied evidence or parsed source | Reading, bootstrapping, patching, and running programs via application services and ports |
| `project_audit.ts` | Finding, scene, and verdict types already in Domain | Audit orchestration in Application; filesystem and process adapters outside Domain |
| `project_file.ts`, `project_memory.ts`, `project_report.ts` | Reuse canonical Project/report contracts; avoid duplicate lifecycle models | Manifest persistence, report assembly, memory loading, and repository access outside Domain |
| `debug_brief.ts`, `debug_wiki.ts` | Pure evidence/knowledge types and lifecycle policy | Evidence extraction, prompt rendering, retrieval, YAML/filesystem persistence in their owning layers |
| `network_api_gate.ts` | Typed observations, not a semantic routing authority | Diagnostic extraction supplies evidence; an owning judge interprets it |
| `language.ts`, `language_project_contract.ts` | Pure language and manifest contracts | Sandbox/process/bootstrap implementations outside Domain; not a permanent exception to layering |
| Locks, storage, cancellation, rendering | Generic pure helpers may stay in the shared kernel | I/O and presentation stay at their existing adapter/infrastructure boundaries |

The pre-migration source demonstrated why a split was necessary:
`project_audit.ts` imports filesystem and Sandbox;
`project_file.ts` imports a concrete repository;
`project_report.ts` imports Application services;
`debug_wiki.ts` loads YAML and writes files.
Moving these files without separating responsibilities is not modularisation.

Start with the planning contracts because other modules consume them. Then migrate a bounded vertical
slice at a time. A file is not ready to move merely because its name sounds like a domain object.
The confirmed responsibility consolidation retains Domain and retires Core without compatibility
wrappers. The current move map and unvalidated implementation are recorded in
[HANDOVER.md](HANDOVER.md); this supersedes the former open directory-name choice.

## Phase B1: explicit instruction contracts

Preserve the agreed vocabulary: `mandatory`, `forbidden`, `required`, `advised`, `announce`.
Do not yet treat its enforcement semantics as settled; see D04 and D05.

A rule needs a stable identity, purpose, applicability, version/content fingerprint, instruction,
and evidence or check contract where applicable. A list groups rules by function. RuleChain is the
global catalogue of these lists; a per-call selection record is separate from that catalogue.

The [RuleChain contract](0.4.0-rulechain-design.md) records confirmed slots and priority. Range indexes
occupy `0x0100`, `0x0200`, and `0x1000`; TS/Python occupy `0x0101`/`0x0102`; six role descriptions
occupy `0x0201-0x0206`. UUIDs identify objects, while lower numeric slots win cross-list conflicts.
Populated base slots `0x0000-0x00FF` are protected and always loaded in business and Rule-selection
requests. Calibration is excluded by confirmed Q0; slot zero remains a declaration only.

The 2026-09-06 continuation confirms YAML definitions with generated/validated indexes (Q1),
manual engineering-source edits plus version updates as the only way to change protected base
content (Q2), and deterministic references/declared-conflict handling (Q3). Referenced lists retain
their slots and applicability. Missing/cyclic references and declared same-list contradictions
error; cross-list conflicts use lower slots. Render Rules by ascending numeric slot, highest
priority first, with visible slot labels and a priority declaration. Ordering supplements the
programmatic checks. Parse and validate YAML before rendering approved fields; source comments
are omitted while literal comment-like characters inside instruction strings remain intact.

Name the existing Application selection/assembly components `RuleSelector` and `RuleDecorator`.
Selector produces applicable effective Rules plus selection/override evidence; Decorator aggregates
that result as Rule content for framework-owned prompt generation. Neither changes rules,
executes Tools or owns business verdicts. Runtime
composes them with the Infrastructure loader and pure Domain contracts. Final request integrity
must still hold after Plugin hooks, compaction and provider fallback. Calibration bypasses both.

The 2026-09-07 clarification confirms one slot per RuleList, lookup of individual Rules within a
list, and Decorator aggregation for framework-owned prompt generation. Four functional categories
are general development/language, compiler framework workflows, functional scenarios such as
Bug/CR judgement, and generated-project business requirements. They do not introduce new workflow
stages or change slot priority. Reusable business rules may be extracted deliberately into scenario
or framework standards; automatic promotion is not approved. Rules govern normal operation;
Wiki retains debugging experience. Their authority and write lifecycles remain distinct.
Existing mixed Wiki content needs source review, as documented in the
[impact review](impact-review.md), before any migration.

The user subsequently approved release-time integration: maintainers curate verified experience
into generalized, reviewed and manually versioned Debug Rules for XCompiler releases. Debug uses
`0x0300-0x0FFF` (3,328 ordinary RuleList slots), while each list can hold many individual Rules.
Use populated catalogue entries and list/Rule lookup to control prompt growth. Keep the existing
three shared Wiki categories, derived-project-local scope, role slots and business index;
this creates no fifth category or extra RuleChain index. See the
[release and growth plan](implementation-plan.md#debug-wiki-and-release-time-debug-rules-confirmed).

Q5 A, confirmed on 2026-09-08, retains actual selected Rule content/versions and retrieval evidence
for each request. Implement exact records and interrupted-write/recovery behavior within that
retention contract; do not introduce a new history-deletion or semantic-proof invalidation policy.

Confirmed contracts to implement:

- Specify RuleList references, index integrity, version authority and storage for Q5 A's request
  records without turning retained selections into another mutable catalogue.
- Apply controlled automatic maintenance: candidates stay with their owning plan/CR; accepted build
  persistence and Project binding activate initial formal Rules, while CR activation follows quality
  evidence and authoritative-tree integration. Preserve old formal versions on failed integration
  and Q5 snapshots for existing requests; no per-Rule human gate or automatic shared promotion.
- Select explicit required bindings separately from optional retrieval. Level does not determine
  recall. Typed applicability uses AND across dimensions and ANY within a dimension; missing
  restricted context excludes optional Rules and explicitly fails uncertain required bindings.
- Define remaining duplicate-application and conflict-evidence fields against confirmed Q3 checks.
- Retain Rule/Skill/Tool boundaries: a Skill composes capabilities; a rule does not execute a Tool or
  mutate a Ticket lifecycle by itself.

Rule selection and typed semantic judgement are both in scope. Similarity, slot priority, mandatory
loading, and evaluation results are distinct. The continuation decision allows direct reuse of an
applicable rubric, followed by the existing owner's current-evidence judgement. A retrieval score
cannot replace a current Bug/CR verdict or deterministic integrity check. Q4 C supplies vector
semantic retrieval plus low-score review, requiring an embedding capability, explicit configuration
and versioned vector index. Items 2 A/3 A select on-demand local indexes, dedicated retrieval
descriptions, bounded task/error summaries and structured context, normalized cosine with an
inclusive initial 0.8 threshold, at most 20 optional candidates and one logical low-score review.
Valid no match continues with required Rules only; service/index/review failure remains an error.
These defaults are approved but uncalibrated. Provider/model values are explicit configuration;
embedding is separate from base-loaded selection chat. Connect the real caller and adapter with
structural checks at that boundary; no lexical scorer or automatic cross-model fallback is implied.

The current Domain catalogue and Infrastructure YAML loader provide schema, immutable lookup,
reference/conflict and source-scope checks, with authored real-filesystem tests. They do not yet
implement request-time selection, vector retrieval, candidate activation or packaged Rule resources.
The existing RuleDecorator still needs final production request integration. Required Router
rejection evidence now propagates typed storage interruption. The subsequent F1 source authors
provider/Router/replay fact capture, while R1 adds pure applicability/conflict primitives with
Application preselection in progress. Completion eligibility, Q5 recovery, full semantic retrieval
and Q6 coordination remain separate implementation work. No tests or gates ran for this checkpoint.
Expanded correction requires the selected per-class lossless transformation proofs.

The [inventory](0.4.0-rule-inventory.md) distinguishes retained instructions, obsolete mechanisms,
pure predicates, and semantic judgements. It is not approved to convert all entries into active rules.

## Phase C: separate existing coordination boundaries

Separate orchestration, pure policy, prompt assembly, and I/O around the current flow. This is a
module refactor, not a new workflow, Ticket taxonomy, or branch strategy. Do not build a generic
nested-flow engine in anticipation of 0.5.

Required design outputs before coding:
- Object ownership and the state transition that owns each operation.
- Step gate completion versus branch promotion versus Phase delivery.
- PM intake, discovery, routing, assignment, and Ticket verification boundaries.
- Existing stage-Story and child-Task behavior, corrective CR propagation, causation, and completion.
- Stage rollback and invalidation of stale downstream evidence.
- Candidate revision, mainline revision, and gate-evidence binding.
- Recovery after interruptions between execution, evidence persistence, state transition, and merge.
- Cancellation, denied permission, dependency/environment blocking, and non-convergence resumption.

The registry remains the recovery authority. Application orchestrates effects through ports and
requests domain transitions; an extracted state machine must not independently persist the same
Project/Phase/Step/Ticket state.

Existing CR propagation remains operational in 0.4. Original failure provenance, replay proof,
scoped edits, worktree evidence, and append-only history must survive the module moves. A mechanism
targeted by a deferred proposal is not dead code and must not be deleted as cleanup.

## Phase B2: enforcement at explicit execution boundaries

After C exposes stable decision points, move inline enforcement into named, typed checks.
Checks return evidence and a structured result; the application-owned flow chooses the legal next
action. Permission waits stay outside provider retry/scoring loops.

Do not turn a factual check into a probabilistic judgement, or a semantic judgement into a regex.
Do not use a generic "safe default" to invent a Bug from malformed model output; D05 records the
required choice and the current behavior.

### Added scope: output calibration (2026-09-05)

Include the [shared output-protocol calibration capability](output-calibration.md). It is not Domain
or business-flow logic: it owns only envelope/completion, JSON syntax, structural shape and eligible
lossless correction. Caller-owned plan, Rule judgement, gate, Ticket and evidence validation occurs
afterwards and never enters Calibration. Its correction prompt is a versioned protocol template,
not a RuleList selected by slot/similarity; deterministic protocol checks remain authoritative. Migrate
Planner, Executor and scenario-judge callers, including current Router feedback, to one explicit
correction-accounting boundary. Do not restore the old combined calibration file or nest another
retry loop around existing ones. This is a 0.4 integration change, not the 0.7 LLM-switch redesign.

Q6 A, confirmed on 2026-09-08, selects the original response's actual producing provider/model and
at most one logical calibration attempt. Transport retries and fallback cannot reset that
allowance. The dedicated-model and two-attempt alternatives are superseded; mechanically provable
lossless transformations, detailed budgets and accounting/integration still require contracts.

## Phase D: consolidated gates

Execute final checks after all approved refactor actions. Define acceptance cases before implementation
so a missing contract is not discovered only after all code has moved.

Cover at least:
- Dependency direction, Runtime-only adapters, and one canonical state authority.
- Every approved Step/Phase gate class, including the initial S1-S3 baseline deferral.
- Multiple independent findings, discovery ownership, PM intake, and scoped routing.
- Current Phase materialisation, stage-Story scheduling, child-Task assignment, and completion.
- Bug repair, original-failure verification, recurrence, and Debug Wiki eligibility.
- Existing candidate/master integration, revision changes, conflicts, interruption, and permissions.
- Rule composition, invalid output diagnostics, bounded corrective feedback, and no silent pass.
- CLI/ACP use of the same runtime behavior, plus package/version checks where affected.

Run the repository's applicable core, integration, end-to-end, static, and build gates. Include
call-site falsification for changed wiring. Line-count reduction alone is not evidence of success.

## Phase E: fresh real-project validation

Use a new 0.4 workspace. An old 0.3 run is historical evidence, not a compatibility acceptance test.
Agree the external-call scope and paid-model spending before starting.

Separate three results: a framework route executed; a repair verified; the product met its Phase
delivery contract. The first is not proof of the latter two.
