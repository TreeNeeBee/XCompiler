without compatibility wrappers. This supersedes the earlier unresolved directory-name choice.
The migration is implemented in the working tree; boundary review and consolidated validation are
still incomplete. The registry remains the single lifecycle recovery authority.

## D03: cross-stage Story identity and completion

**Deferred:** the user has assigned Story/Task redesign to 0.5, where Story becomes a functional item
with its own V-model. A Story used only as a cross-stage change carrier may conflict with that
meaning. Reconsider this proposal as part of the [0.5 design](../0.5.0/0.5.0-functional-stories-and-v-plus-v.md);
do not implement it or remove `workKind` in 0.4.

**Confirmed facts:** `workKind` currently exists only on Epic/Story/Task and has four values:
`phase`, `v-model-step`, `planned-work`, `delivery`. A stage's `v-model-step` Story already
represents that stage and cannot also represent an unscoped cross-stage change.

Earlier proposed name: `cross-stage-change`, PM-owned, without a single executable `stepId`.
The name, schema, and use of Story as the carrier are not approved.

Earlier consumption alternatives, conditional on approving a carrier model:
- **A: advancing review.** Every downstream stage reached by the V model receives a
  stage-local CR for the Story revision. The owner records applied or evidence-backed not-applicable.
  Close only after the required stage receipts and designated delivery verification succeed.
- **B: declared impact.** Record affected stages up front; only those receive CRs. Lower repeated
  review cost, but omitted impact requires an explicit scope revision and revalidation.
- **C: hybrid.** Declare likely impact and require a lightweight impact verdict elsewhere. More
  machinery, but lets the cost of full CR execution follow the impact finding.

All alternatives need:
- Stable Story identity, origin finding/Ticket, accepted delta, requirement, and source revision.
- Unique materialisation keyed to Story revision and the approved stage-execution identity.
- Re-entry behavior for rollback, already-consumed stages, failed local CRs, and interrupted writes.
- A completion contract distinct from Bug resolution and Step delivery.
- Multiple concurrent Stories: ordering/conflict handling, cancellation, and supersession.
- Original Bug replay and Debug Wiki provenance retained after the old CR chain is removed.

Deleting propagation fields without an approved replacement would lose obligations, not simplify
them. Keep the current carrier and flow operational in 0.4.

## D04: RuleChain catalogue, priority, and enforcement

**Confirmed 2026-09-04:** RuleChain is the global RuleList catalogue, not a per-execution subset.
RuleLists group rules by function and may reference other RuleLists. Global UUIDs provide identity;
RuleList slot numbers provide location and priority. Lower slots win cross-list conflicts.

The [RuleChain contract](0.4.0-rulechain-design.md) records the complete allocation:
- `0x0000` is an Asimov declaration, not an executable permission or gate policy.
- Populated `0x0000-0x00FF` slots are protected and always loaded in business and Rule-selection
  requests. Calibration uses only its fixed protocol template, as explicitly confirmed in Q0.
- `0x0100`, `0x0200`, and `0x1000` are exclusive range-index blocks.
- TS is `0x0101`, Python is `0x0102`; the earlier TS=`0x0100` allocation is superseded.
- `0x0201-0x0206` hold Planner, Architect, Coder, Tester, Debugger, and ProjectManager respectively.

This supersedes the earlier context-specific-chain representation alternatives and leaves no separate
per-Rule numeric priority decision. The later Q3 decision below settles reference priority and
declared same-list conflict handling.

**Confirmed in the 2026-09-05 continuation:** high similarity may directly select an applicable
instruction or judgement rubric; it must not reuse a historical verdict as the current result.
An existing semantic-judgement owner evaluates current accepted context and current evidence using
the selected rubric. Extracting the scenario rubric does not add a second business-judgement call.
Deterministic gates, permissions, PM routing and Ticket transitions keep their current owners.
The existing scenario prompt's Bug/CODE preference when evidence does not establish a contract
change is preserved, independently of the parser rejecting malformed judgements.

This supersedes the open choice about direct reuse of historical judgements. Retrieval similarity
is not judgement validity, and base mandatory loading is not a numerical threshold pass. The user
has authorized planning and implementing the settled contracts; this does not select defaults for
the remaining policies listed below.

**Q0 confirmed by explicit user choice:** correction requests exclude base content and business
RuleLists and do not invoke RuleChain selection. The fixed versioned protocol template alone governs
correction. This supersedes the literal every-prompt base-loading wording.

**Q1-Q3 confirmed in the 2026-09-06 continuation:**

- Q1: use YAML definitions to support author comments, with generated/validated indexes. Prompts
  receive approved parsed instruction fields and Rule metadata, not raw YAML files or comments.
  Preserve comment-like characters and line breaks that belong to instruction strings.
- Q2: protected base content is immutable to Runtime, models, Plugins and generated projects. Like
  source-controlled constants, it changes only through manual engineering-source edits and a
  version update. No Runtime-managed automatic update mechanism is authorized.
- Q3: use deterministic reference and declared-conflict checks. Missing/cyclic references and
  same-list contradictions error; referenced lists retain their own priority and applicability.
  Resolve cross-list declared conflicts by lower slot. The user separately confirmed ascending
  numeric slot presentation, highest priority first, with each rule's slot and a priority declaration

**2026-09-07 clarification:** one RuleList occupies one slot and supports lookup of individual
Rules. RuleSelector supplies related effective Rules and evidence; RuleDecorator aggregates them
for the framework's prompt generation, preserving owning-list metadata. There is no multi-slot
mounting choice left. Domain, Infrastructure and Runtime retain their existing boundaries; Q0
excludes calibration from both components.

The user distinguished general development/language Rules, framework workflow Rules, specific
functional-scenario Rules (such as Bug/CR judgement), and generated-project business/special Rules.
Reusable business standards may be extracted into scenario/framework standards. This does not
authorize automatic promotion or erase project scope. Category and slot remain distinct concerns;
no new scenario slot range was allocated. Normal-operation Rules and debugging experience in Wiki
retain distinct authority and write lifecycles. Existing mixed Wiki text requires source review;
it is not automatically an authoritative Rule.

**Release-time integration subsequently approved:** verified Wiki experience may be deliberately
selected, generalized, reviewed and manually versioned as Debug Rules in XCompiler releases.
Preserve the three shared Wiki categories and derived-project-local storage; raw experience does
not acquire Rule priority. The requested larger Debug segment is `0x0300-0x0FFF`, containing 3,328
ordinary RuleList slots under the framework index. Each list can hold many Rules. Keep
`0x0207-0x02FF` for other framework lists and `0x1000` as the business index. Sparse catalogue and

**Q4 C confirmed in the subsequent reply:** use vector semantic retrieval plus low-score model

**Remaining-decision items 2 A and 3 A confirmed on 2026-09-10:**

## D05: invalid LLM output and uncertain attribution

**Confirmed documentation error:** the current scenario parser does not default missing/out-of-enum
routing fields to Bug/CODE. It rejects them, and Runtime retains an unjudged failed Phase gate.
The earlier roadmap described a default that the code does not implement.

**Scope update 2026-09-05:** include flexible LLM-assisted output-protocol correction in 0.4. This supersedes
the earlier description of all automatic correction as an unapproved feature direction. It does not
approve arbitrary parser guesses, semantic changes, execution of repaired fragments, or new retry
and scoring defaults. See [output calibration](output-calibration.md) for the proposed contract.

The current implementation already has plan calibration, parser-side `jsonrepair`, Planner repair
feedback and Router-driven LLM correction. Only diagnostic advice was migrated into Wiki. Consolidate
these responsibilities instead of restoring a second monolithic calibration module.

The boundary is protocol-only: envelope/completion, JSON syntax and permitted structural shape.
Business schema semantics, plan validity, evidence, gates, permissions and Bug/CR classification
remain with the caller. A protocol-valid business rejection returns to the producing role and must
not be sent to Calibration. Every corrected candidate repeats protocol checks and then traverses the
caller's unchanged validation path. Failed correction remains an explicit output failure; it cannot
invent a product defect, fabricated evidence, or execute a salvaged partial action.

## D06: ChangeSet and MergeRequest

**Deferred:** both models remain in use during the scoped 0.4 refactor. Consolidation has no assigned
implementation release and is not implicitly included in 0.5 V+V.

**Confirmed limitation of the original argument:** observing equal counts in one run does not prove
the two concepts are equivalent. ChangeSet represents candidate work; MergeRequest represents its
review/promotion request. `MergeGateRun` binds a verdict to exact revisions.

- **A:** retain both concepts but remove competing ownership of delivery state. A proposed change to
  stage/master promotion boundaries remains part of the separate branch discussion.
- **B:** use one ChangeSet delivery lifecycle while preserving independent GateRun evidence, exact
  revisions, repeated rejected submissions, and durable merge intent. This was favored in the later
  architecture discussion for a single-target delivery unit, but the user has not approved it.

Equal object counts do not justify either choice. Multiple targets, abandoned requests, evidence
invalidation, recovery after a Git merge, and future provider mirrors need explicit contracts.

Also disambiguate `rootTicketId`: Ticket uses it for the Phase Epic; ChangeSet uses it for the branch
owner. A shared spelling is not evidence that those IDs have the same meaning.

## D07: shared dev and merge recovery

**Deferred:** not part of 0.4 Rule/module work and not automatically scheduled for 0.5.

The permanent-dev direction does not yet define:
- What revision each corrective branch starts from.
- How a rollback works when dev already contains downstream modifications.
- Whether stage processing is serialized and how future parallel writers are coordinated.
- What proof is invalidated when dev changes after a gate.
- How interrupted promotion or user edits are reconciled without resetting or discarding data.

Recommended starting point: pin a corrective branch to its discovery revision on dev; serialize
promotion, bind evidence to the exact candidate and master revisions, and re-evaluate after a
conflict or revision change. This is a proposal awaiting the branch contract, not an authorization
for destructive Git operations.
