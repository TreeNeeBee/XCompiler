## 3. 详细发现

### RC-01：验证 Step 补写测试时缺少适用的语言规则

**触发场景。** 单元测试等验证 Step 的声明产出只有报告，例如 `docs/05-unit-test.md`；执行器仍可在 Runtime 分配的补充测试目录中编写测试。TypeScript 的 Vitest API、导入扩展名、冻结时钟规则，以及 Python 的相关测试约束，现已从系统提示迁入按路径限定的 Rule。

**调用链与原因。**

- [Runtime 请求入口](../../src/runtime/execution_turn_request.ts) 第 188～196 行，将 `step.outputs` 原样作为 Rule 的产出上下文。
- [AttemptRunner](../../src/application/execution/attempt_runner.ts) 第 774～780 行，分配补充测试根目录并加入允许写入范围。
- [Executor](../../src/agents/executor.ts) 第 864～873 行，保留先编写补充测试、再执行冻结门禁的流程。
- [TypeScript 规则](../../rules/language-typescript.yaml) 的 `vitest-only`、`ts-import-specifiers`、`frozen-clock` 和 [Python 规则](../../rules/language-python.yaml) 中相应条目依赖测试／源码产出路径。

仅声明报告的 Step 不满足上述路径条件，因此即使将要补写测试，也不会得到这些指导。

**复现证据。** 使用当前真实目录、绑定、选择器、装饰器以及执行器系统提示，构造 `verify.unit`／`test-engineer` 请求，产出仅为上述报告，工具为 `read_file`、`write_file`、`run_tests`：

- TypeScript 语言条目仅剩 `dev-dependencies`、`test-file-names`、`config-ownership`；组合后的提示不含冻结时钟指导。
- Python 在该输入下没有语言条目，组合提示不含对应的 `conftest.py` 和时钟指导。该输入未提供 `add_dependency`，不能据此断言所有 Python 验证请求均为零条目。

**影响与边界。** 缺失的是测试 API、导入和时间等具体约束；并非所有 Vitest 提及都消失。这里证明了指导遗漏及实际补写测试能力，没有用真实模型运行证明一定生成错误代码。

合同第 11.4 节明确规定 `paths` 是“Step 声明的产出”。因此这属于规则内容与执行能力组合后的覆盖缺口，不能简单把 Runtime 复制 `outputs` 判为实现错误，也不能未经确认就把所有允许写入路径改作产出。

**建议与验收。** 明确补充测试行为如何匹配语言规则，例如使用相应工作维度，或提供单独且受控的补充测试上下文。修复后应通过实际验证请求入口证明：只声明报告但会补写测试的 TypeScript／Python Step 获得必要规则，纯文档且不补写测试的工作仍正确过滤。

### RC-02：升级后的槽位碰撞同时阻断加载与丢弃差异

**触发场景。** 用户在旧安装尚未占用的槽位创建本地 RuleList；新版基础目录在同一槽位新增了另一个 UUID 的列表。

**原因。** [差异合并逻辑](../../src/application/rules/rule_overlay.ts) 第 111～115 行对本地新列表只检查同 ID 基础列表，没有识别不同 ID 占用同一槽位；随后 [有效目录加载器](../../src/infrastructure/rules/effective_rule_catalogue.ts) 第 24～28 行构造完整目录，抛出 `invalid_rule_catalogue / slot_conflict`。[丢弃入口](../../src/runtime/rule_maintenance.ts) 第 153～158 行先调用 `loadRuleState`，所以用于恢复的 `discard` 也被相同错误阻断。

**复现步骤与结果。**

1. 在临时安装副本中模拟旧基础目录，暂不包含当前 Python 列表占用的 `0x00001002` 槽位。
2. 在该槽位创建有效本地列表，确认旧有效目录可以加载。
3. 保留差异文件，改用当前完整基础目录。
4. 调用真实 `checkRules` 和 `discardRuleOverlay`：两者均因 `slot_conflict` 失败，差异文件仍在。

这是受控的升级条件模拟，并非真实历史安装包之间的升级测试。

**影响与边界。** 需要重新加载有效目录的新业务请求会失败，维护命令也无法完成正常恢复。已固定快照的请求不一定重新加载目录，不能概括为所有进行中的请求都会失败。

**建议与验收。** 升级冲突应能以可审查的状态报告，同时保留导出／丢弃等恢复能力。具体碰撞处理策略需要明确后再实现。至少覆盖“不同 UUID、相同槽位”的升级与恢复组合，不能仅测试同 UUID 的基础摘要变化。

### RC-03：失败重试将类型化类别退回为文案匹配

**触发场景。** 上一次失败已经具有结构化类别；重试时，将它渲染成反馈文本，再用该文本构造新的 Debug 简报，并把重新推断的类别传入 Rule 上下文。

**调用链与原因。**

- [失败策略](../../src/application/execution/attempt_policy.ts) 第 342～350 行的 `briefForAttemptFailure` 正确传入 `typedFailure`；第 353～378 行将简报渲染为重试反馈。
- [AttemptRunner](../../src/application/execution/attempt_runner.ts) 第 459～468 行再次调用 `buildDebugBrief`，只传反馈文案，没有传入已有类型化失败；第 497～498 行使用其类别作为 `failureCategory`。
- [Debug 简报](../../src/application/execution/debug_brief.ts) 第 61～63 行在缺少 `typedFailure` 时使用文本推断，第 197 行起的分类逻辑包含错误文字匹配。

**复现证据。** 使用同一结构化失败 `{ category: 'test', code: 'test_command_failed' }`，按实际调用点的辅助函数顺序运行：

| 失败文字 | 原类型化简报类别 | 重试重建后的适用类别 |
|---|---|---|
| `ModuleNotFoundError: No module named parser` | `test_failure` | `import_error` |
| `The same test import could not be resolved` | `test_failure` | `exception` |

该验证执行了实际辅助函数并追踪生产调用点，未运行完整 Runner 端到端场景。

**影响与边界。** 同一类型化失败仅改变文案，就会改变按 `failureCategories` 筛选的 Rule；也可能与 Debug Wiki 使用的类型化简报不一致。本地维护功能允许编写这种限定规则，因此并不限于未来的向量选择。原有重试摘要已经存在文本重建；本轮新增的风险是将重建结果用于 Rule 的确定性适用判断。

**建议与验收。** 保留生产者已给出的类型化失败／最新失败简报作为控制字段，文案仅用于展示与证据压缩。增加从 Runner 到实际规则选择的覆盖，证明只改变错误文字不会改变类别和选中规则；同时覆盖首次修复与同 Ticket 后续重试。

### RC-04：快照缺少本地差异的完整来源证据

**合同。** 修订合同第 4.4 节要求快照与审计记录实际生效内容，以及“基础版本和摘要、差异记录的摘要”。

**原因。** [有效目录加载器](../../src/infrastructure/rules/effective_rule_catalogue.ts) 第 27 行仅把差异来源标为 `{ owner: { kind: 'local' }, location }`。[来源 schema](../../src/domain/rules/catalogue.ts) 第 210～217 行也仅允许 owner 与 location。[快照 schema](../../src/application/rules/rule_request_snapshot.ts) 第 35～48 行保存有效列表版本和上述来源，未保留对应基础摘要、差异摘要的不可变身份。

**复现步骤与结果。**

1. 对现有 system-architect 角色 Rule 添加本地正文标记。
2. 加载有效目录，完成 `bound-only` 选择，通过真实文件存储保存草稿与快照。
3. 删除差异文件，再读取快照。
4. 本地正文标记仍在，快照可正常恢复；但快照材料中找不到原基础摘要和差异摘要，来源仍仅指向已删除文件。

**影响与边界。** 历史有效正文恢复正常，这不是此前 SNP-01 内容丢失问题复发。缺口是差异被覆盖、丢弃或发布后，无法仅凭持久证据核对它究竟基于哪个基础内容、来自哪份差异记录。快照有诸如 `2.0.0+local.1` 的有效版本，不能说完全没有版本信息；但这不能替代合同要求的完整来源证明。

**建议与验收。** 在目录来源与持久审计边界保存经过校验的基础身份及差异摘要。覆盖修改、再次更新、丢弃和发布后的历史读取，证明追溯不依赖可变差异文件继续存在。

### RC-05：`promote` 丢失 YAML 作者注释

**合同。** 修订合同第 4.3 节要求结构化读写 YAML 并保留作者注释和顺序；使用 YAML 的原始选择也明确考虑了注释。

**原因。** [发布维护入口](../../src/runtime/rule_maintenance.ts) 第 284 行调用 `renderRuleListYaml` 重写文件；[序列化实现](../../src/infrastructure/rules/rule_source_format.ts) 第 56～70 行从普通对象重新生成 YAML，未保留原文档的注释节点。

**复现。** 在临时源码副本的 TypeScript 列表 `rules:` 前加入作者说明注释，正常修改其中的 Vitest Rule，再执行真实 `promoteRuleOverlays`。发布前注释存在，发布后消失。注释不参与内容摘要，因而此输入本身有效。

**影响与边界。** 发布本地改动会删除维护者的说明与依据。此处确认的是注释丢失；未据此断言 Rule 作者顺序也全部丢失。

**建议与验收。** 对已有 YAML 保留文档结构并更新对应字段，新列表再走完整生成。覆盖块注释与行尾注释，并继续保证注释不进入模型提示。

### RC-06：`promote` 后列表引用仍固定在旧本地版本

**触发条件。** 两个有效本地列表 A、B，A 引用 B 的精确本地版本 `1.0.0+local.1`，一起发布回源码。

**原因。** [发布定义转换](../../src/application/rules/rule_overlay.ts) 第 303～312 行调整列表及 Rule 版本，却沿用原 `references`。[维护入口](../../src/runtime/rule_maintenance.ts) 第 279～292 行逐列表写入、更新清单，随后删除已应用差异，没有在最终版本引用关系上完成整体目录校验。

**复现步骤与结果。**

1. 使用当前 schema 与真实差异存储，构造 A 引用 B 的有效本地 YAML；发布前完整目录校验通过。
2. 执行真实 `promoteRuleOverlays`，返回成功。
3. B 发布版本变为 `1.0.0`，A 的引用仍为 `1.0.0+local.1`。
4. 重新加载生成的完整 YAML 目录，得到 `invalid_rule_catalogue / reference_version_mismatch`；两份差异已被删除。

**影响与边界。** 该路径可能产生无法加载的源码目录，而且用于发布的本地差异已经移除。当前 26 个发布列表没有列表引用，`create-list` CLI／API 也没有暴露引用参数；本复现使用人工构造、经 schema 校验有效的差异。因此属于已支持数据结构下的潜在发布缺陷，不是当前默认目录必然失败。

**建议与验收。** 先确定整批发布后的版本及引用关系，校验完整结果，再写入和删除差异。精确版本引用如何迁移应明确约定。覆盖新增列表互相引用、引用已存在且版本变化的列表，以及失败时差异证据仍可恢复的场景。

### RC-07：Unicode 查询长度在构造与持久化之间不一致

**合同与原因。** 修订合同第 11.2 节规定摘要按码点限制到 2,000 字符。[查询构造](../../src/application/rules/rule_selector.ts) 第 56～59 行用 `[...text]` 按码点截断；[快照校验](../../src/application/rules/rule_request_snapshot.ts) 第 52～54 行的字符串 `.max(2000)` 按 JavaScript UTF-16 长度计数。

**复现。** 使用真实选择器的 `review` 策略及有效开放段候选，输入 `'😀'.repeat(2001)`。构造后的摘要为 2,000 个码点、4,000 个 UTF-16 代码单元，随后 `createRuleSelectionDraft` 报 `rule_snapshot_failed / invalid`，底层原因为 `query.taskSummary` 超长。复现没有调用真实评审模型。

**影响与边界。** 合法截断后的查询仍可能无法保存。当前 0.4 配置只开放 `bound-only`，该路径不构造相关性查询，因此不是默认业务流程的现有阻塞项；应在开放 `review`／`embedding` 前修复。

**建议与验收。** 统一构造、草稿和快照的计数单位，按已写明的码点合同校验。覆盖普通中文、非 BMP 字符及混合摘要在边界两侧的行为。

## 4. 需要单独确认的设计边界

### 4.1 评审完整性错误只阻断第一次，重试后降级

CC 审计报告第 4 节第 4 项明确披露：评审阶段遇到审计写入、回放、配置等非服务错误，第一次会抛出；但一次评审认领仍保留，下次同请求因 `review_incomplete` 降级，只带必需条目继续。

这是“完整性错误应继续阻断”与“一次评审后不再发起调用”如何共同实现的设计边界，不能因为代码已有行为就视为用户已批准。建议把服务不可用与完整性错误分开：前者按批准的降级策略处理，后者保留明确失败状态与原始原因；最终重试策略需要用户确认。当前默认 `bound-only` 下不触发评审，本项不计入上述 7 个确定性缺陷。

### 4.2 其余待确认事项保持原状态

CC 已披露的三份内容草案、Python 最小规则集与入口规则位置、TypeScript 配置归属的模式范围等，仍需按原合同审定。纯文本 Rule 格式已有结构测试，但未经过真实模型验证，不能由字符串测试推导出模型一定正确理解优先级或防伪造边界。

本报告不替用户批准这些设计，也不把所有待确认事项重复列为新缺陷。

## 5. 已核对的有效实现与范围限制

- 当前 schema 2、32 位槽位、双语材料、分组渲染、最小规则集及适用维度均有实际实现和测试；审计问题主要发生在它们组合后的边界。
- Rule 正文按摘要存储后，删除本地差异仍能恢复已保存的有效正文。RC-04 指向来源追溯缺口，不否定正文保存能力。
- 此前 E／SNP-01 的快照保护在既定范围内成立：同一个 Runtime 请求端口保留固定摘要；快照与草稿同时丢失时拒绝重新选择；仅快照丢失时可从草稿重建并核对摘要。相关集成测试覆盖真实业务调用点，防止额外发送。
- 上述保护不能等同于完整的进程重启恢复。生产流程接入重启恢复入口仍是 CC 已披露的未完成项，本报告未将这一既知范围误列为本轮新回归。
- D-20 真实项目验证、原生二进制打包和发布均未在本轮完成。当前结论不代表发布验收通过。
