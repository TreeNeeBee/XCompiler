## 原因与证据

### 1. Python 路径加载被误判成未调用产品代码

`tests/unit/test_warnings.py` 为避免与标准库同名模块冲突，使用 `Path(__file__).resolve().parents[2]` 定位工程，再经 `importlib.util.spec_from_file_location`、`module_from_spec`、`exec_module` 加载 `src/warnings.py`。测试随后调用这个模块的公开接口。

原 `pythonProductReferences` 只识别普通导入及进程调用中的路径。它不认识上述加载链，错误地报告 `exercises 0/1 required declared product sources`。这也是首次日志诊断需要更正的部分：三份被拦测试中有一份确实在测试 P2 源码。

修复增加静态路径加载识别，检查路径表达式、加载 spec、模块创建、执行及成员使用之间的联系。支持字面量路径、`Path(__file__)`、`parent`/`parents`、路径拼接、简单别名及返回模块的加载函数；不能静态确认的表达式仍不计入。检查本身不执行派生工程 Python。普通导入和 TypeScript 检查保留原行为。

在原候选 `8548ded` 上重新检查，`test_warnings.py` 已被识别为引用 `src/warnings.py`。把同一测试文本中的 `exec_module` 调用断开后，识别结果重新为空。

### 2. 运行时摘要被展示成可读取的工作区文件

Runner 把重试摘要放入名为 `.xcompiler/retry/CR-P2-001.md` 的片段，但没有创建这个文件。提示渲染器却把所有片段都放在“已有文件”的段落下。第八次尝试实际调用 `read_file` 读取该标识并得到 ENOENT，随后因重复只读操作停滞。Ticket 快照、架构摘要、下游说明和补充测试诊断存在相同边界问题。

新片段带 `source: workspace | runtime`。Runtime 材料单列为内联证据，明确其标识不是工作区文件，不能通过文件工具读取或写入。原始内容仍随请求留存；压缩历史时不把它作为文件预览淘汰，Bug/CR 无改动移交也不能据此声称已读取某个文件。

新字段为可选字段，已捕获且没有来源字段的旧请求保持原渲染。回环请求、留存恢复和 provider 投影测试覆盖新旧两种输入，恢复不重新发送模型请求。

### 3. 两份测试确实没有覆盖 P2 声明的模块

`tests/unit/test_excel_writer.py` 和 `tests/unit/test_cli.py` 与 P1 交付版本一致，分别调用 `dbc_excel.excel_writer` 和 `dbc_excel.cli`。P2 设计及计划声明的是 `src/excel_writer.py` 和 `src/main.py`。当前 `src/main.py` 仍转调旧 CLI。

因此，两项门禁继续失败有实际依据。本次没有修改导入路径来制造通过，也没有取消对已交付回归断言的保护。门禁修复提示改为补充或局部修改行为测试，并提醒修改已交付测试必须提供已接受的 `contractBasis`，避免笼统要求“重写测试”。

候选提交 `b63d675`、`4a0932d`、`f8ada1c` 和 `8548ded` 的 Git tree 均为 `d73cf2a7169cfe47c1b7b3788b63b7e850fddaaa`。反复通过现有测试并未改变这两项缺口。原始审计还记录了缺少契约依据和整文件覆盖被拒绝的工具结果。
