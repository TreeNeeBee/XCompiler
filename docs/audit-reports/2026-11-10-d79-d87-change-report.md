## 3. 逐项变更

### D-79 · 整组获准后才登记契约依据（RR-01，`4493b78`）

- **问题**：整组判定获准后仍逐条登记依据。组未执行完时，文件的中间内容也带着有效登记，D-76 又允许跨 Ticket 复用登记。
- **处理**：`checkTurn` 为每个获准的组记录未完成的写入，最后一条写入成功后，才按最终内容一次登记全组。任何一条失败、被拒或中断，整组都不登记。执行器改为工具执行成功即调用 `record`，内容未变的成功写入也算完成。
- **影响范围**：`attempt_runner.checkTurn`、`executor.ts` 的写入回调。
- **证据**：真实 git 加真实 attempt runner：部分完成不登记，全部完成后登记最终哈希。真实 StepExecutor：第二条写入失败时不登记，交付复核拦下。

### D-80 · 按测试所属阶段的交付版本判定（RR-02，`4493b78`）

- **问题**：“交付时的测试”读的是当前 Ticket 基线，可能已经包含之后其他 Ticket 的修改。
- **处理**：`Phase.deliveredRevision`（可选）在交付时记录；`readAsDelivered` 按测试所属的前序阶段读取它。未记录的旧阶段，退回到下一阶段各 Ticket 基线提交的 `merge-base --octopus`；两者都没有时不提供，而不是给出错误版本。
- **影响范围**：Phase 模型、`ProjectController.completePhase`、判定材料。需求文档仍从 Ticket 基线读取。
- **证据**：三步历史下，判定看到的是 P1 内容（直接读取与退回两种情况都测了）。dbc2excel-5 的退回结果是 `79142d9`，它和 P1 交付清单提交之间没有测试改动。

### D-81 · 判定材料整份发送，否则不判定（RR-03，`4493b78`）

- **问题**：材料按 8,000 字符截断，而真实测试文件有 8,889～9,783 字符。
- **处理**：上限改为测试 32,000、修改 24,000、需求 32,000 字符。超限时不判定：修改超限提示分轮进行，测试或需求超限作为 finding 上报。构造消息时再检查一次，超限直接抛 `ContractBasisEvidenceTooLargeError`。
- **证据**：真实消息构造函数能整份发送 9,000 字符以上的内容，前缀相同、尾部不同的两份内容能区分；超限时不调用判定。

### D-82 · 验证 Step 自己的补充测试，失败归它自己修（`4493b78`）

- `inherited_test_change_unregistered` 按类型码分支：被改动的文件（`details.paths`）都属于该验证 Step 的补充测试（本阶段的或继承的）时，留给它自己处理，不再交给没有写权限的开发 Step。归属判断与测试失败归属共用 `ownedSupplement`。

### D-83 · 失败列表不截断（`4493b78`）

- `run_tests` 的结构化 `failedTests` 改用不截断的 `failingTestsIn`，摘要仍只显示 8 条。修复选择器、“是否全部属于本 Step”的判断都基于完整列表。

### D-84 · 阶段交付打发布标签（用户决定，`4493b78`）

- 交付后，在交付修订上打附注标签 `v<n>.0.0`（第 n 个阶段；同一阶段再次交付时修订号递增；同一提交已有标签则复用）。只打在生成工程的本地仓库，不推送；打标签失败只写审计，不撤销交付。
- `GitRepositoryService.releaseTags`（附注标签取其指向的提交）、`createAnnotatedTag`；`ProjectOrchestrator.tagRelease`。
- dbc2excel-5 的 P1 在 `5ba0229` 上手动补打了 `v1.0.0`。

### D-85 · 验证 Step 修好自己的 Bug 后就地关闭（真实 run 发现，`1ec9b88`）

- **问题**：`P2-S008` 修好了自己继承的补充测试，`BUG-P2-011` 却以“没有下游验证路径”停止。原因是 S008 是最后一个 Step，下游为空就停。
- **处理**：`CorrectiveWorkflowService.closeCorrectiveProvenAtOwnStep`。当以下条件同时满足时，交付 Step、记录改动与方案，经 `closeBugsProvenAt` 关闭 Bug：
  - 纠正修复已通过，且下游为空；
  - Bug 的验证合同指向本 Step，且本 Step 是验证 Step；
  - 本轮测试结果满足合同；
  - 没有以该 Bug 为源、仍未关闭的 CR 链。

  Step 不在这里关闭，由排在 Bug 后面的 Story 或 CR 恢复后关闭。条件不满足时不改任何状态，仍以 `no_downstream_verification` 停止。
- **证据**：引擎测试复现了原停止；修复后 Bug 关闭；修复尝试没跑 Bug 点名的用例时，仍然停止且不关闭。第 7 次续跑中按预期关闭了 `BUG-P2-011`。

### D-86 · 合并冲突如实报出，过时的一代由属主重跑（真实 run 发现，用户选“检测修复加 A-收窄”，`012e33d`）

- **问题一**：simple-git 的 `raw()` 遇到冲突的 `git merge` 不抛错，因为冲突信息写在 stdout。门禁候选其实就是主干本身，门禁记录 `cand == tgt` 却显示 `passed`，直到 squash 提交才失败，又被当成基础设施问题 `blocked`。
- **问题二**：冲突原本按可修复失败处理，修复留在同一条过时分支上，再合并仍会冲突。
- **处理**：
  - `runMerge` 在候选合并和 squash 之后都读取 Git 状态，有未合并路径就抛 `MergeConflictError`（候选合并会先 `merge --abort`）。
  - `MergeIntegrationService.resolveConflict` 同时接住门禁候选和 squash 两个冲突点。后者用来处理那些在未合并候选上“通过”的旧记录。
  - 满足以下全部条件时，ChangeSet 转为 `abandoned`、MR 转为 `closed`，释放工作树，分支保留，返回 `superseded`：
    - 属主 Ticket 仍会再运行（`created`、`in_progress`、`pending`、`reopened`）；
    - 这一代切出（`changeSet.createdAt`）之后，属主没有 `verified` 提交；
    - 这一代切出之后，所有纠正 Ticket 的 `verified` 提交都在属主要重跑的 Step（`workStepId`）上。
  - 不满足时返回 `conflicted`，编排器以 `merge_conflict`（分支、冲突文件）停下。
  - 编排器三处集成点：单张交付后、启动时恢复“门禁已通过”的几代、阶段交付。遇到 `superseded` 写审计后继续；遇到 `conflicted` 写审计后停下。启动时废弃其中一代，其余照常合并。
- **影响范围**：`git_repository_service`、`merge_integration_service`、编排器、`RunStop`、i18n。领域状态机不变。
- **证据**：
  - 测试：真实 git 的冲突检测；一个 e2e 场景（属主的下一代从最新主干切出）；三种停下情形；切出前的交付不计入；编排器三处入口。
  - 证伪 20 处。
  - 离线复演和第 8 次续跑都按预期废弃了 r2；调度器下一项正是 `CR-CR-043 @ P2-S008`。

### D-87 · 发布包含自己的用户文档、报告和准确的文件清单（终审 F-1、F-2、F-4、F-5，用户决定，未提交）

- **问题**：
  - F-1：P2 起用户文档写在 `docs/iterations/<阶段>/`，根目录 README、快速上手一直停在 P1；阶段门禁检查根目录，所以“通过”。
  - F-2：清单写进了 P1 的功能测试文档。
  - F-4：开发报告在打标签之后才生成，每个阶段的发布都不含自己的报告。
  - F-5：清单取自工程文件树，收录了被忽略的 `.xc-tmp`、测试缓存（181 项，实际只有 100 个文件）。
- **处理**：
  - 时点不变：仍在所有 Step 关闭之后、交付关闭之前组装（`onStepsClosed`）。`domain_scheduler` 的测试锁定了“清单属于交付记录本身”这一点。`publishDelivery` 依次执行：
    1. `promotedUserDocs`：把本阶段 README、快速上手（库项目含 API 指南）复制到根目录。源文件缺失时记 `domain.user_doc_promotion_skipped`，不报错。
    2. `writeDeliveryReport` 钩子生成报告。报告新增 `delivering`：正在交付的阶段（最终交付时还有项目）按已交付判定结论。报告失败只记审计。
    3. 有待提交内容时提交，提交说明为 `publish delivery documents`。
    4. 用 `releaseFiles(该提交)` 加上交付文档本身作为清单，写入 `deliveryDocForIteration` 指向的本阶段交付文档，再提交。
  - 随后照旧读取交付修订、关闭阶段、打标签。标签、交付修订和含报告的提交三者一致。
  - `runProjectAudit` 的文档检查改为按 `plan.phaseId` 取本阶段的交付文档。
  - `calibrateDocPaths`：新计划中，P2 起的功能测试 Step 要产出本阶段 README。plan lint 不要求它，已有计划照常加载。
  - `run.ts`：提供 `writeDeliveryReport`、`releaseFiles`，删除交付后再生成报告的代码。运行结束时，`collectDeliveryListing` 从记录和仓库回读，`renderDeliveryListing` 打印本阶段交付清单；项目全部交付时追加整体项目清单（用户补充的要求）。
- **证据**：
  - 测试：真实 git 集成测试 3 例；引擎测试（报告先于两次提交，标签和交付修订都落在最后一次提交上）；运行层接线测试；单元测试若干。证伪 13 处。
  - 离线回放（dbc2excel-5 副本，回到 `25270ca`，放回真实的被忽略目录）：根目录文档换成 P2 版本；清单 101 项，与发布文件一致，不含被忽略文件；P1 文档不变；报告进入发布，结论为 `DELIVERED`。

## 4. 对其他功能的影响

| 变化 | 影响 |
| --- | --- |
| 交付收尾多一次提交（D-87） | 交付修订现在是“清单”提交，它的父提交包含提升后的文档和报告。D-80 用这个修订判定测试改动，这两次提交都不改测试 |
| 报告从运行结束挪进交付（D-87） | 每个阶段交付都会生成报告，并进入发布。报告失败不再让 run 失败（之前是交付完成后才失败），改为记审计 |

| 合并冲突的结果（D-86） | 不再为冲突开 quality-gate Bug，改为 `superseded` 或 `conflicted`。`failed` 只用于门禁检查失败 |
| 新增停止原因 `merge_conflict`（D-86） | 终端用当前语言显示，记录里保持英文 |
| 纠正工单的新关闭路径（D-85） | 只在 Bug 的验证合同指向本 Step、且下游为空时生效 |
| 新计划的功能测试产出（D-87） | P2 起多一项本阶段 README |

## 6. 已知问题与未处理项

1. **D-86 留下的记录不一致**：`BUG-P2-011` 已关闭，但它的修复所在的那一代被废弃，没有合入主干。主干上有等效修复，`CR-CR-043` 在主干上重跑的 S008 测试集包含该 Bug 点名的用例。审计事件中列出了它的编号。
2. **D-86 收窄的边界**：属主已经在这一代上交付，或者有纠正 Ticket 在其他 Step 交付时，不会自动处理，而是以 `merge_conflict` 停下，需要人工决定。
3. **D-87 尚未经过真实交付**，第一次真实检验将在新目录的完整验收中。
4. **D-87 的报告“正在交付”判定**：报告在 `onStepsClosed` 时写出，此时 `completePhase` 的关闭条件已全部核对。之后关闭交付和史诗工单时如果出错，报告会写着已交付，阶段却没有关闭。这种情况会让 run 以错误结束，可以从审计中看到。
5. **RR-01 的残留**：判定通过后，如果某条写入执行失败，文件会停在中间状态（不带登记，交付复核会拦下）。
6. **早先记下的未处理项**：判定模型质量、同层产出文档能否作为依据引用、G3 其余部分、CR 逐级回走的成本、终审 F-3（P2 文档示例中的警告条数写错）。
7. **终端提示“Plan 全部完成（1/8）”**：其中 1 是本次运行执行的尝试数，8 是 Step 总数，措辞有歧义，未改。
8. **测试环境**：三组测试同时全量运行时，个别慢用例会超过 20 秒；分组运行和单独运行都通过。

## 7. 请审计重点关注

1. **D-79**：执行器调用 `record` 的时机，与工具“执行成功”的定义是否一致；组的拼接（相连写入的并集）是否会漏掉某条写入。
2. **D-80 与 D-87 的组合**：交付修订现在晚于提升文档和报告的提交，确认判定读取的测试内容不受影响。
3. **D-85**：关闭条件会不会在 Bug 实际未被证明时关闭它；Step 留在 delivered，由谁关闭，有没有遗漏的情形。
4. **D-86 的资格判断**：以 `verified` 提交的 `recordedAt` 对比 ChangeSet 的 `createdAt`，时间戳格式或时钟是否会造成误判；按纠正 Ticket 的 `workStepId` 判断是否足够；启动时废弃一代后继续合并其余几代的顺序是否安全。
5. **D-86 的 `runMerge`**：合并命令抛错但同时留下冲突时的处理；squash 失败后 `reset --hard` 的回滚；候选合并的 `merge --abort`。
6. **D-87 的时点与内容**：组装放在 `onStepsClosed` 是否守住了“清单属于交付记录”；清单等于“第一次提交的文件加上交付文档”是否在所有情况下都等于最终发布的文件；`commitPendingDelivery` 没有待提交内容时不提交，是否会影响交付修订。
7. **D-87 门禁文档检查的变化**：对进行中的 P2 工程是否构成功能回退，或只是如实暴露了缺失。
