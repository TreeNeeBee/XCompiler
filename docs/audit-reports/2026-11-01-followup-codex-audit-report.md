## 3. 确认问题

### FU-01：覆盖率路径没有真实路径约束，目录符号链接仍导致项目外删除

**优先级：P1。属于上一轮 XC-01 的残留边界，不是调用方路径修复失效。**

位置：[src/tools/sandbox.ts](../../src/tools/sandbox.ts) 第 276～278 行；后续读取在第 302 行。固定路径定义在 [src/sandbox/test_args.ts](../../src/sandbox/test_args.ts) 第 29～32 行。

#### 触发条件

Python 门禁使用正常的 `PYTHON_COVERAGE_ARGS`，项目目录中已有 `coverage/` 符号链接，指向项目根目录之外。来源可以是已有工程、人工操作或此前运行的项目脚本；调用方不需要传入自定义覆盖率参数。

#### 根因

本轮把报告来源从合并后的运行参数改为 `gateArgs`，阻止调用方直接指定 Runtime 清理的路径。但 `path.resolve()` 只做字符串路径解析，不阻止父目录符号链接跳出工作区：

```ts
const coverageReport = pytestCoverageReport(gateArgs);
await fs.rm(path.resolve(runDirectory, coverageReport), { force: true });
```

这里未经过工作区真实路径检查。`coverage/coverage.json` 的文本形式虽然固定，实际被删除的文件仍可能位于工作区外。随后读取覆盖率的调用使用相同的未约束路径。

#### 已执行复现

在同一个临时父目录下创建：

```text
project/
  tests/test_gate.py
  coverage -> ../outside
outside/
  coverage.json        # 原始内容为 DO NOT DELETE
```

调用真实 `runTestsTool.run({}, ctx)`，其中：

```text
ctx.ws.root = project
ctx.language = python
ctx.testGateArgs = [tests/test_gate.py, ...PYTHON_COVERAGE_ARGS]
```

runner 进入时只检查外部文件是否存在，然后返回失败；不启动测试进程、不删除文件。结果：

```json
{
  "deletedBeforeRunner": true,
  "victimExists": false,
  "gateArgs": [
    "tests/test_gate.py",
    "--cov=src",
    "--cov-branch",
    "--cov-report=json:coverage/coverage.json"
  ]
}
```

这直接证明删除由 Runtime 在 runner 执行前完成。后续读取缺少同类约束由源码确认；本轮未另行证明外部文件内容泄露。

#### 影响

- 用户批准运行测试，并不意味着允许 Runtime 删除工程之外的覆盖率文件。
- 删除发生在宿主的工具代码中；不能依靠后续测试进程的沙箱弥补这一边界。
- 固定报告名限制了目标文件名，但未限制其真实目录；正常项目目录未包含越界链接时，不触发本反例。

#### 建议与验收

清理前约束报告文件及现有父目录的真实位置；读取前同样验证边界，避免测试运行期间替换目录后读到工作区外。优先沿用已有路径约束机制，并保留明确的拒绝原因。不得在越界后继续运行并把该文件作为覆盖率证据。

回归至少覆盖：正常报告生成、调用方绝对/相对外部路径、固定报告目录指向外部、运行期间报告目录被替换。对外部目录的反例应证明文件字节不变；删除清理前的约束调用必须使该用例失败。是否允许仍指向项目内部的符号链接，应遵循现有路径合同，实施时不能顺带改变策略。

### FU-02：历史真实失败会使当前无结论调用被误接受为延后验证

**优先级：P2。D-64 A2 的单次无结论场景已修复，多次调用场景仍未覆盖。**

位置：[src/agents/executor.ts](../../src/agents/executor.ts) 第 2361～2368 行；完成判断的调用点在第 1466 行附近。新增单次场景测试位于 [tests/executor.test.ts](../../tests/executor.test.ts) 第 1602 行起。

#### 触发条件

上游修复 Step 有 `deferredVerificationScope`、真实修改证据及完整质量评估。在同一次 `StepExecutor.run` 中，先有测试执行失败，再经修改后调用测试，但最新调用因为参数错误、缺失输入等没有获得测试结论。模型随后把剩余问题归因下游并声明完成。

#### 根因

`hasExecutedFailure` 使用 `calls.some(...)` 查找整个尝试历史中的任意一次真实测试失败。新加的 `isTestRunWithoutVerdict` 仅排除该次候选历史记录。

随后对**当前未解决失败**只检查 key 是否以 `verification:run_tests:` 开头，并没有检查这些记录自己的 `code`、权限状态及其是否仍有可延后的有效测试结论。旧失败即使后来已经通过，也仍保留在历史调用数组中，足以让 `hasExecutedFailure` 为真。

#### 已执行复现

沿用新增 A2 测试的上游修复配置，使用真实 `StepExecutor`、`write_file`、`run_tests`。临时工程门禁固定为 `tests/test_gate.py`，测试断言 `src/x.py` 的内容等于 `x = 5`。

每次测试之前均通过真实写工具修改产物，避免把“重复未修改的命令被拒绝”误当成本问题。最后一次传入 `--tb=not-a-style`，由真实 pytest 返回 exit 4，真实工具生成 `test_run_without_verdict`。模型响应由确定性替身提供。

| 实际 pytest 退出序列 | 当前结果 | 预期结果 |
|---|---|---|
| `[4]` | `success=false`，未延后 | 正确，保持未完成 |
| `[1, 4]` | `success=true`，接受延后 | 不应接受当前无结论调用 |
| `[1, 0, 4]` | `success=true`，接受延后 | 旧失败已被通过消除，更不能替当前调用提供延后依据 |

后两项结果中，执行器还把质量评估的 `failedTests` 从 1 改成 0，并加入：

```text
Paired FUNCTIONAL_TEST Step S008 remains deferred; its failed tests are recorded in tool evidence and blockedBy, not counted as failures of the current upstream Step.
```

原始 exit 4 和失败码仍保留在工具调用记录里；问题发生在完成与移交判断，而非原始证据被删去。未声称已经在完整项目编排链中证明最终发布会通过。

#### 影响

本应由当前 Step 修正的测试调用错误被作为下游问题移交，当前 Step 可能提前报告成功。后续阶段可能重新遇到参数或输入问题，造成无效传播，并使质量评估与当前测试证据不一致。

#### 建议与验收

延后资格应针对当前仍未解决的测试失败及其范围判断，不能用已被后续结果替代的历史失败作通行条件。当前未解决记录存在无结论或权限控制结果时，应保持对应调用未完成，并保留原始记录。

回归应通过 `StepExecutor.run` 覆盖上述三种序列，再覆盖“真实失败后修复并通过”的正常完成路径，以及不同测试范围相互独立的情况。撤掉完成路径中对当前失败状态的检查，混合历史用例必须失败；仅测试孤立判断函数不足以证明接线正确。
