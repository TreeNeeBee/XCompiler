## 2. 已确认的根因

### 2.1 单元测试成功被当成另一个集成测试成功

生产审计在 `2026-11-16T17:01:15.735Z` 记录六个 unit 文件 `156 passed`。随后 `17:01:16.139Z` 请求另一条 integration 选择器时，执行器只判断代码变更代次已验证，直接返回成功，没有运行该请求。模型据此声称目标集成用例通过。

该复用分支由 `4543a37` 引入，`ee83d53` 后来拆分 baseline 代次标记，仍未把请求参数纳入复用条件。工具层还有刻意保留的固定门禁：丢弃模型自选路径，执行 Runtime 的范围。因此仅取消缓存，仍可能把实际单元门禁当作对另一范围的回应。

本轮通过真实 Python 子进程复现：集成测试直接运行失败；修复前经执行器先跑 unit 再请求 integration，只运行 unit，最终仍成功。修复后不同范围明确拒绝，不产生新范围的执行判定，反复请求该范围不会完成。

### 2.2 重复拒绝分支丢失结构化结果

修复中再次运行原始复现发现：第一次越界拒绝之后，合法请求可以解除调用错误；若同轮再次请求同一越界范围，旧的重复验证分支只保留错误字符串，没有恢复尚未解决的错误。这可能导致后续完成判断放行，并丢失“尚无测试判定”的类型。

现改为保存完整 `ToolResult`，重复请求时保留类型和原结果，并重新登记未解决错误。只修正调用方式可以解除范围误用；真实测试失败仍按实际运行范围处理。

### 2.3 诊断缺少当前候选证据，旧驳回结论被精确恢复

原诊断仅依据历史失败与处理方陈述。该工程的旧 verdict 引用的行号和失败已与当前候选不符，但同 CR、同候选会复用该 verdict。恢复同一请求身份是正确边界，删除旧回复强迫重发会破坏审计，因而需要显式的新证据轮次。

### 2.4 派生工程还有独立的业务问题

前一轮对候选 `9e9458d0feb5bb140cd9a6c12f4f590de24f4252` 的调查确认：

- `src/main.py` 仍进入旧 P1 CLI，新辅助函数未接到真实入口；独立 CLI 缺少 P2 列，非法标记输入仍整体失败。
- P1/P2 同名 `excel_writer` 顶层导入造成执行顺序依赖。
- 非法标记 pipeline 用例自己生成警告并过滤信号，单例通过不能证明产品完成这一行为。
- 当前详细设计已经明确 M006 的真实入口职责，以及不得由测试实现这些产品转换。

原候选复测结果为：保存的 32 个选择器 26 通过、6 失败；原 S6 文件/目录范围 47 通过、5 失败；P2 CLI 文件独立运行 6 个均失败；非法标记 pipeline 单例通过。范围和导入顺序不同，结果不能互相抵消。这些是本轮之前的调查证据，不是本轮新完成的 S6 正式验收。

## 4. 显式复核流程

1. 只接受当前进行中 Phase 内、第一轮为 dismissed 的 CR 诊断；核对源 CR 仍活跃，workspace binding 仍是该候选，reporter 仍为原验证者。
2. 在 Phase 的原 `problemReview` 中保存 `recheck.afterRequestId` 与时间，不删除旧 verdict。
3. 读取候选文件，沿既有授权路径在 detached worktree 重放原失败范围；执行失败保留为证据，权限/执行异常不伪造结果。
4. 追加第二轮，保留原证据与原判定，加入候选及重放证据，生成新的逻辑请求 ID；在请求模型前持久化。
5. 原验证者通过自己的模型池独立判定。确认缺陷则按既有关系创建纠正工作；再次驳回立即停止当前运行，之后普通重启也不调度同候选的处理工作；仍需证据则停止，不再加轮次。
6. 普通重启恢复已授权操作；第二轮已保存则复用其身份和材料，已有 verdict 不再请求。`--dry-run` 只校验资格，不开启复核。

重放是诊断证据，不能用于关闭 CR 或源 Bug。原 Bug 仍须等下游 CR 验收，再由原 S6 reporter 正式复验。
