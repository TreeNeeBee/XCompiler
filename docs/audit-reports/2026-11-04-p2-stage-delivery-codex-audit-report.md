## SD-01 · P1 · 失败的 pytest 可以让项目门禁通过

**复现方法。** 在临时目录运行以下测试，使用现有业务验证环境的真实 pytest，保留原始 stdout 和退出码。

```python
def test_regression():
    print("=== short test summary info ===")
    print("1 passed")
    assert False
```

pytest 返回 1。它先在失败报告中回显捕获的两行 stdout，随后才输出真正的摘要和 `1 failed`。将此结果送入生产入口 `runProjectAudit`，读取真实 P2 计划及文档，固定入口探测成功并省略场景评审，以单独观察测试门禁。

| 输入给审计入口的证据 | 测试检查 | 项目审计 |
|---|---|---|
| 真实 stdout，退出码 1 | 整个检查消失 | `ok=true, errors=0` |
| 只去掉捕获区的两行，保留同一退出码、失败详情及最终摘要 | 生成失败的 `tests:code` | `ok=false` |
| 对照回放上轮 39 项真实失败的 stdout，携带 P1 所有者及 P2 计划 | 生成六组失败检查 | `ok=false` |

**根因。** 解析器从第一个形似摘要标题的行开始，再把含有通过或失败数量的第一行当作最终计数。测试打印的 `1 passed` 使失败数为零，恰好等于已收集的零个用例，解析器遂返回“完整”。分组函数对空集合返回零个检查，原来已由退出码判定的失败也随之消失。最终门禁只计算剩余检查中的错误数。[摘要定位与计数](../../src/application/delivery/project_audit.ts#L298) · [失败分组](../../src/application/delivery/project_audit.ts#L239)

**验收条件。** 对任何非零退出或超时，项目门禁必须至少保留一项失败检查。分组可以补充失败证据，无法获得可信、非空的用例列表时应保留原始失败。通过生产入口同时验证上述反例、正常参数化用例及 39 项历史样本，并断言最终门禁状态。

## SD-02 · P2 · 旧登记可以覆盖同一文件后来的无依据改动

写入路径先核验依据并写入 Ticket，之后才询问权限、执行工具。用户拒绝写入、工具失败或尝试回滚时，声明可以留在账本中。交付复核将整个 Ticket 的登记投影为路径集合，只要当前变更的文件名出现过，就视为已登记。[派发顺序](../../src/agents/executor.ts#L1089) · [交付复核](../../src/application/execution/attempt_runner.ts#L1350)

**独立复核。** 在临时 Git 仓库提交一份含警告断言的继承测试，随后将断言替换为 `assert True`。直接调用生产交付复核方法，使用真实 Git 差异和受控 Ticket 读取结果。账本为空时，返回该文件为未登记。账本提供相同路径、早先尝试、不同 Step 和另一修改理由时，返回空列表。该实验覆盖最终判定函数。此前拒绝写入、随后通过程序副作用改写的完整顺序，依据派发源码推导。

**影响与验收条件。** “回滚也留审计记录”本身符合追溯要求。问题是同一记录随后能充当另一笔修改的交付依据。应分别保留声明历史与本次交付证据。用一次被拒的合法写入和一次随后发生的未登记副作用验证，后者仍须触发 `inherited_test_change_unregistered`。同时保留正常重试能复用同一份实际改动依据的路径。

## 报告中的保护范围需要收窄

- **功能层同样可能引用无关条款。** 使用生产 `resolveContractBasis`，从真实业务提交 `8cb9fbe` 读取 P2 需求。给功能测试填写“允许失败输入产生警告”的理由，却引用“前 16 列与 P1 完全一致，第 17-19 列为 P2 新增。”，结果为 `ok=true`。层级检查确实能拒绝功能测试直接引用概要设计，但同层无关需求仍会通过。用户已选择推迟语义校验，应把此限制写为适用于所有层级。[依据解析](../../src/application/execution/contract_basis.ts#L62)
- **CR 验证了接受状态，未校验此次测试是否在变更范围中。** 真实接受列表限定同一项目、同一 Phase 的根契约 CR，并检查关闭、验证和集成证据。解析器随后只匹配 Ticket ID。本轮给解析器提供一条“更名 CLI 帮助标题”的受控已接受记录，作为放宽警告断言的依据，结果被接受。这说明关联检查缺失，实验没有冒充真实业务 CR 已经越权执行。[接受列表](../../src/application/execution/accepted_contract_changes.ts) · [CR 引用分支](../../src/application/execution/contract_basis.ts#L57)
- **Ticket 基线只阻止同一 Ticket 在基线之后新写文字再引用。** 前一张 Ticket 已写入并进入后一张 Ticket 基线的矛盾附录，依然可以成为下一张 Ticket 的逐字依据。CC 已披露该边界。业务侧 D1 的两个附录和已放宽的 P2 自有测试 T1 仍需单独验收。[基线读取](../../src/application/execution/attempt_runner.ts#L1308)
- **旧对象兼容性。** 对实际业务仓库中缺少 `contractBases` 的 204 个 Ticket 首版记录执行新 `TicketSchema` 解析，204 个全部得到空数组。证据支持历史对象的读取兼容性，完整重启恢复、后续写回和再次交付未在本轮演练。[Ticket schema](../../src/domain/tickets/ticket.ts)
