## 交付为何停在 P2

| 失败数 | 直接原因 | 验收依据 |
|---:|---|---|
| 19 | P1 断言仍要求固定 16 列，P2 已追加 3 个 J1939 字段 | 保留前 16 列的名称与顺序断言，同时核对追加的三个字段。 |
| 11 | P1 测试用二元组解包 `process_files`，P2 接口返回行、错误和警告三项 | 按三元组读取结果，继续检查原有行与错误语义。 |
| 9 | 失败文件产生了额外的「警告」工作表 | 文件解析失败后应保留该文件的错误，丢弃其未提交的警告。成功文件的有效警告仍应保留。 |

产品缺陷位于派生工程 `src/main.py:79`。调用方把共享的警告列表交给解析器。解析器向其中追加记录后仍可能抛错，异常分支只追加错误，已写入的警告因而进入最终工作簿。9 个失败观察到的是这一个行为在多个测试范围的表现。

修复过程中，派生工程的 `docs/03-high-level-design-p2.md` 第 382 和 391 行出现两份同名附录。第一份要求失败时丢弃该文件的警告，第二份允许保留。模块测试也放宽到接受现有行为。局部测试可以据此通过，但两种契约仍然矛盾。README 与 quickstart 继续描述 16 列，README 还写明不支持扩展多路复用和 J1939。交付门禁记录的文档检查只验证文件存在。

run A 最后因服务响应超时结束。run B 中，Step 已交付，阶段全量测试才暴露跨阶段回归。旧门禁向路由提供的输出尾部只显示最后一个失败用例，历史资产在 P2 缺少明确可写的负责方。审计记录显示，BUG-P2-004 的修复没有改动文件，下一次门禁又报出同一问题，触发 `repair_recurred_unchanged`。该停止条件准确反映了重复失败。D-66 改善了截断和失败补丁后的反馈，D-67 让无效 finding 能按字段纠正，两者都没有改变这次阶段门禁的资产归属。

## 未提交修复的四项发现

### F-01 · 高 · 按测试所有者分组后直接判为产品缺陷

**已通过生产门禁入口复现。** 将真实 pytest 输出、P1 测试所有者和 P2 计划传给 `runProjectAudit`，新的门禁识别出全部 39 例，并按详细设计 4、概要设计 12、需求分析 4、CODE 12、功能测试 6、集成测试 1 生成六组。每组都使用 `product-defect` 类别，并把测试所有者设为修复目标。[门禁分组实现](../../src/application/delivery/project_audit.ts)

例如，`tests/unit/test_cli.py` 同时暴露旧接口解包和失败文件警告泄漏。它们归属于同一个测试文件，修复却分别落在测试调用方和产品实现。反过来，同一个警告泄漏又会被拆给多个 Step。验收时应能从各组追溯全部用例，区分已批准的契约迁移与实现错误，并让一个根因关联多个受影响用例。

### F-02 · 高 · 写权限和 CR 完成判断使用不同的资产清单

**源码调用路径已确认。** 当前尝试从历史 Phase 收集同层资产并加入 `allowedWrites`。执行器判断 CR 是否涉及本 Step 时，`currentStepAffectedArtifacts` 却只遍历当前 `step.outputs`。一份只由 P1 声明的文件因此可能允许修改，却不会被识别为本 Step 必须处理的 CR 产物。[尝试权限](../../src/application/execution/attempt_runner.ts) · [权限计算](../../src/application/execution/execution_context.ts) · [CR 完成判断](../../src/agents/executor.ts)

现有用例验证了权限计算和 PM 路由。仍需通过真实 CR 执行路径证明，当受影响产物只有一个继承的旧测试时，执行者不能仅以“不归当前 Step”为由结束工作。[现有继承测试](../../tests/inherited_test_assets.test.ts)

### F-03 · 高 · 改动历史测试后，当前 Step 的验收可能漏跑该测试

**源码调用路径已确认。** 新权限允许同层 Step 写历史基线或补充测试目录。验证器构造的执行集合仍来自本次配对基线和本 Step 的补充根目录。只存在于 P1 的测试即使被本次改动，也没有因这次修改而自动进入验收集合。[历史资产范围](../../src/domain/quality/test_assets.ts) · [验证集合](../../src/application/execution/test_phase_validator.ts)

验收反例可以使用一份 P2 修改的 P1 测试。令该测试失败、当前 P2 配对测试通过，检查 Step 是否在交付前执行并保留旧测试的失败结论。F-02、F-03 的端到端发生频率尚待验证。

### F-04 · 中 · pytest 日志正文能冒充用例，部分真实用例 ID 却被漏掉

**已用构造输出通过生产门禁入口复现。** 输入包含测试正文打印的一行 `FAILED tests/not-a-case.py::bogus - printed by test`，以及真正的 pytest 摘要行 `FAILED tests/test_cli.py::test_x[with space] - AssertionError`。门禁只报告了 `bogus`。解析器扫描整个标准输出和错误输出，且只接受无空格的用例 ID。这个反例中，失败总数仍显示为 1，单独比较计数无法发现身份替换。[摘要解析](../../src/application/delivery/project_audit.ts)

验收应检查用例身份和来源。参数化 ID 需要完整保留，测试正文中的相似文本不得生成可路由的 finding。若证据不完整，应在门禁记录中明确体现。
